## 摘要（先看这里）

指南在**工程契约层面质量较高**：代码签名、坐标约定、API 清单、烟雾测试流程、反刷分规则都写得明确，且提前用一句话否定了"连子获胜"的误解。规则内核也做到了前后端单一事实源、余额不足抛异常而非静默失败——工程素养在线。

但本次分析共定位 **13 项问题**，其中 **3 项高危**。高危项的共同特征是：**指南没说的比说了的更重要**——关键机制藏在公开源码里，而文档给的是近似描述。

| 类别 | 问题数 | 高危 | 中 | 低 |
|---|---|---|---|---|
| 指南歧义 / 缺失 | 8 项 | 2 | 3 | 3 |
| 规则与机制设计 | 5 项 | 1 | 2 | 2 |

**三个最需要修复的问题**：
1. **「送上门不吃」示例的因果解释是错的**——内核只按**颜色序列**判定，根本不存在"送上门"这条规则。照示例的思路推理会在别的局面得出错误结论。
2. **「无合法走法自动 pass」与 `legalMoves` 契约存在缺口**——`Rules API` 没有"是否还有合法走法"的判定接口，而 pass 会**悄悄推高 `noCaptureMoves`**（作者看不到）。
3. **先手在均势下偏劣 + 终局大量以子力裁定收场**——本地 200 局同强度自对弈**全部和棋**，胜负常由开局选点的随机抖动而非中盘棋力决定。

# 第一部分：指南中的歧义与不清楚之处

## 1.1【高危】「送上门不吃」的示例与官方内核实际行为不符

**指南原文**（§吃子示例 · 第二条）：
> **送上门不吃（黑方刚走）**：本手前 (1,1)、(2,1) 为红（已 2 连），(0,2) 为黑；黑子从 (0,2) 下移到 (0,1)，横线 y=1 变为 (0,1) 黑、(1,1) 红、(2,1) 红、(3,1) 空。这是「对方 2 连 + 己方 1 子」，但本手是**黑方**走棋、吃子只能由走棋方触发，故 **(0,1) 的黑子不被吃**。

**问题**：结论（不吃）是对的，但**给出的理由与内核的真实判定逻辑不符**，属于"结论对、推理错"。按官方内核逐字复算该局面（实测输出）：

```
落子后横线 y=1：(0,1)黑 (1,1)红 (2,1)红 (3,1)空
占位 [0,1,2] → 恰好 3 子、连续 ✓
v = [黑, 红, 红]
内核分支（game-rules.js:56-57）：
  v[0]===side(黑) && v[1]===side(黑) ? 否
  v[0]===opp(红)  && v[1]===side(黑) ? 否
→ 不匹配任何吃子形态 → 不吃。【实测确认 captured=[]】
```

**关键差异**：内核**根本不判断"谁是走棋方"来决定吃不吃**——它只判断**这条线的三子颜色序列**是否匹配 `(己,己,敌)` 或 `(敌,己,己)`。走棋方身份已经**隐含在落点颜色**里了（因为落点上一定是走棋方的子）。

因此指南那句"**吃子只能由走棋方触发，故 (0,1) 的黑子不被吃**"是一个**错误的因果解释**——它把一个"颜色序列不匹配"的结果，归因成了一个"时机/主体"的判断。**如果作者照这个思路去推理，会在别的局面得出错误结论。**

**真正会踩的坑**：指南把这条命名为「送上门不吃」，暗示存在一种"对方送来的子不能吃"的通用规则。但内核里**根本没有这条规则**。真实情况是：

> 吃子只结算**本手落点所在**的横线与竖线；只要那条线上恰好 3 子且连续、颜色序列匹配两种模板之一，**无论这 3 颗子是何时、怎样摆成的，都会被吃**。

**反例（实测确认）**：同一局面若把红子换成黑子，使线上成为 `(黑,黑,红)`——黑子从 (0,2) 落到 (0,1) → **红子 (2,1) 当场被吃**（`captured=[[2,1]]`）。可见"送上门"与否与吃子无关，**颜色序列**才是一切。

**危害**：高。这是**唯一一条给错因果解释的示例**。作者若据此建立"送上门"概念，会在自研搜索里写出一条不存在的规则分支，或者错过"利用对方上一步送出的形态"的进攻机会。

**建议**：删掉这条示例（它不构成独立规则），改为统一表述：
> 只结算本手落点所在横线与竖线。该线恰好 3 子且连续时，仅两种序列可吃：`(己,己,敌)` 吃末位敌子、`(敌,己,己)` 吃首位敌子。`(己,敌,己)` 与 `(敌,敌,己)` 均不吃。**与这三颗子是何时刻、由谁摆成无关，只与序列有关。**

## 1.2【高危】「无合法走法时引擎自动停一手，不调用你的代码」——与 `legalMoves` 契约冲突

**指南原文**（§棋类规则要点 · 第四条）：
> 无合法走法时由引擎自动停一手（pass），**不调用你的代码**。

同指南 §代码契约 又写：
> 返回 `game.legalMoves[0]`。

**问题**：两句话在"极限局面"下**无法同时成立**：
- 若引擎真的在 `legalMoves.length === 0` 时不调用 `onTurn`，那作者永远不需要处理空数组；
- 但 `legalMoves` 是**运行时快照**，作者在搜索中自实现规则内核时，必须**自己**判断"当前是否无着可走"。而指南给出的 `Rules API` 中**没有 `isTerminal` / 无着可走的判定接口**（`judge(board, ncm)` 只按子力与 ncm 裁定，不告诉你"是否还有合法走法"）。

**实测数据**【已证实】：本地复刻引擎 `harness.js` 的对局循环（复刻官方 `play_session` 语义）中，**无着可走的分支会 `ncm++` 并切换行棋方，但该分支根本不会进入"调用 agent"的代码路径**（第 108-118 行）。也就是说——

**真实实现是**：引擎在无着可走时**确实不调用**你的代码。但由此产生一个更隐蔽的坑：

> **`game.noCaptureMoves` 在"对方 pass 了一手"时会 +1，而你的 `onTurn` 看不到这个 pass 事件**——因为 pass 发生在两回合之间，引擎不给你任何回调。你在第 N 手看到的 `noCaptureMoves` 可能已经因为对手的一次隐形 pass 而跳变。

**危害**：
- 作者若在自研搜索里**自己**实现"连续互停 → 按子力裁定"，需要**额外**判断"双方都无着可走"，而指南的 `judge` 不做这件事，容易判定成"继续走"而永远搜不到终局；
- 反过来，若作者**完全信任**"无着可走引擎会兜底"，在自研 `legalMoves` 生成器与官方有偏差时就会返回非法手 → 当场判 illegal 负（这正是烟雾测试最主要的失败来源）；
- **pass 会悄悄推高 `ncm`**：你只看得到 `game.noCaptureMoves` 的当前值，却看不到其中**有几步是对手的隐形 pass 贡献的**——收盘计时可能被你算错。

**实测数据（补充）**【已证实】：`pass` 并非"几乎不可达"。本地 200 局随机对局中，有 **2 局（1%）出现无着可走**（每次约 2.5 手）。本人 1057 手真实回放中 `pass:true` 出现 **0 次**，因此**真人/强脚本对局中极罕见，但不能按"永不发生"来写代码**。

**建议**：
1. 明确写"`onTurn` 只会在 `legalMoves.length > 0` 时被调用，但你**不得**假设自己的走法生成器在任何局面都有输出"；
2. 在 `Rules API` 中补充 `hasMoves(board, side)`，或在文档中明确"用 `legalMoves(b,s).length === 0` 判断"；
3. 补充说明 pass 事件是否会体现在 `noCaptureMoves` 递增上（【已证实】：会，且作者无从察觉具体在哪一回合发生）。

## 1.3【中】`board[x][y]` 用「列优先」描述，措辞与计算机语义冲突

**指南原文**：
> **棋盘是列优先二维数组，用 `game.board[x][y]` 访问**：第一维是 x（横坐标/列），第二维是 y（纵坐标/行）。

**问题**：表述的**后半句完全正确**，但"列优先"（column-major）在计算机语境中特指**扁平数组的线性化顺序**（`index = x*H + y` 之类）。这里 `board` 是**两层嵌套数组**，叫"列优先"会让熟悉该术语的作者误以为存在一个扁平化索引需要自己算。

**危害**：低，但指南自己已经点明"最常见的错误是按 `board[y][x]` 读"——说明这块**确实是新手高发区**（本人 v1 阶段亦踩过），措辞应进一步降低歧义。

**建议**：改为——"`board` 是嵌套数组 `board[x][y]`，**第一维为 x（横向列索引）**，第二维为 y（纵向行索引）。请勿与扁平索引混淆。"

## 1.4【中】终局条件「连续 20 手无吃子」——「手」的定义未在术语表中固定

**指南原文**：
> 连续 20 手无吃子按子力裁定，领先 1 子即判胜（material）。

**问题**：指南在不同位置混用了「手」「回合」。此处写"手"，规则内核是 `ncm >= 20`，而 `ncm` 的递增发生在**每一个 ply**（含 pass 也会 `ncm++`）。也就是说：

**真实行为**【已证实，源码 `judge(board, ncm)`】：
- 阈值是 **20 个 ply（单步，双方各算一步）**，即约 **10 个完整回合**；
- `ncm` 在**吃子发生时归零**，**pass 时也递增**；
- 关键在于 `ncm` 的**起始与递增时机**：落子吃子 → `ncm = 0`；未吃子 → `ncm + 1`；无着可走 → 也 `ncm + 1`。

**危害**：中等。作者若按"20 回合 = 40 手"规划收官（例如"我领先，还有 40 手可以拖"），实际只剩 20 手——**收官预算整整打对折**，会在该稳住时贸然求变。反向错误同样致命：落后方以为"还有很久"，结果被对方用一次吃子归零（见 2.2）后重新计时，反而获得翻盘窗口。

**建议**：在术语表固定「手 = ply = 单方一步」，并把终局条件改写为"**连续 20 个 ply 无吃子**"；同时明示 `ncm` 在吃子和 pass 时的不同处理。

## 1.5【中】计分单位是「场」还是「局」——指南未显式说明

**指南原文**（§正式挑战与段位分）：
> 双局制（执黑、执红各 1），双局合计定本场胜负。
> **反刷分**：同一对代码哈希之间，正式挑战**前 10 场**计入段位/战绩，之后为练习赛不计分（响应 `scored:false`）。

**问题**：这里有三层单位混用且都叫"场"：
- 「**前 10 场**」——这个"场"指一次挑战（含 2 局）；
- 「双局合计定**本场**胜负」——同一处又指一次挑战；
- 而 RP 结算「胜 +25 / 平 +10 / 负 −15」是按**场**给分的。

**实测数据**【已证实，本人线上记录】：计分粒度**确实是"场"（= 1 次挑战 = 2 局双局制）**。挑战响应中的 `scoringNote` 明确给出"该哈希对还可计分 N 场（共 10 场）"；按 `bot.info` 的 W/L/D 反推（W19 L2 D8 与 20 次挑战吻合）确认双局合计。**单局得分 2 分、和局 1 分**，故"黑胜 3 + 红和 1 = 3:1 → 挑战胜"。

**危害**：**这是最容易误算"还剩几次涨分机会"的地方**。作者若把"前 10 场"理解为 10 局（= 5 次挑战），会在实际还剩 5 次计分机会时就以为用尽而放弃；反之若理解为 10 次挑战，则会误判为还剩更多。

另有一个**未说明但极易踩的坑**（【已证实】本人 v3 事故）：
> **每步挂钟是"每局累计"，不是"每手"**。指南只说"每手设有挂钟超时（数秒级）"，实际实现是**单局累计预算**——v3 配置 700ms/手 在约 9.1s 处被判 `runtime` 负；v2 配置 ~7s 安全。作者按"每手 700ms × 30 手 = 21s 也没事"来估算是**完全错误**的。

**建议**：
1. 把「前 10 场」明确为「前 10 次挑战（每次 2 局）」；
2. 把挂钟从"每手数秒"改为明确写"**每局累计挂钟上限约 X 秒**，超出当回合判 runtime 负"，并给出具体数值（哪怕给区间）。

## 1.6【中】`History` 字段的内容与用途「疑似」未定义

**指南原文**（§代码契约）：
> `game: { board, turnNumber, noCaptureMoves, legalMoves, history, random }`

API 一览中的 `GET /api/match/{urlId}` 说明是"含逐手棋谱"。

**问题**：`game.history` 是**运行时**传入的字段，但指南**从未说明它的元素结构**——是 `{from,to,captured}`？是否含 pass 项？是否含对手的隐藏动作（暗棋博弈里这会泄露信息，本棋无隐藏信息所以问题较小）？是否可从它可靠地反推 `noCaptureMoves`？

**实测数据**【已证实】：真实回放中的 `history` 元素结构为
```json
{"turn":8,"side":"red","from":[2,0],"to":[2,1],"captured":[[2,3]],"pass":false}
```
即含 `turn / side / from / to / captured / pass`。**但这是"回放接口"的 history，不能证明"运行时 game.history"同构**——两者可能不同（回放是完整版，运行时可能截断或阉割）。

**危害**：中。作者若想用 `history` 做**开局库匹配**或**重复局面检测**，需要依赖其结构稳定。本人最终实现**完全没依赖 `history`**（改用自维护的键），正是因为无法确认其运行时契约。

**建议**：给出 `history` 元素的确切 schema 与长度上限（是否截断？是否含 pass？）。

## 1.7【低】「防守/进攻」等策略性措辞未定义，但指南未承诺给策略

**评价**：指南在 §良好 Agent 行为 中给了"读榜 → 侦察 → 改进 → 提交 → 挑战 → 复盘"的推荐循环，属于**流程建议**而非**规则约束**，措辞清晰。

**唯一小问题**：它推荐"用侦察接口读对手近期棋路、针对性备战"。但**同一段又承认对局非确定性（每场随机种子）**。本人实测【已证实】：当**双方脚本都近似确定性**时，不同 seed 的**前 47 手逐手完全相同**（分叉只出现在已败定之后）——也就是说：

> **"非确定性"在强确定性脚本对局中几乎不产生差异，反而让"侦察 + 硬编码开局"成为高收益 meta。**

这与指南"侦察只能把握风格倾向，无法精确预测具体某盘"的表述**存在张力**：实测下，只要对手是确定性脚本，就能**精确预测每一盘**。这不算文档错误，但属于**指南对 meta 的乐观描述与实测不符**。

**建议**：如实说明"若对手脚本高度确定性，侦察可精确到逐手复现；去随机化（引入多套等价开局轮换）是有效的反侦察手段"。

## 1.8【低】`capturedCount` 语义与「被吃子颜色何时公示」未说明

**指南原文**：
> `me / opponent: { side, pieces, capturedCount }`

**问题**：未说明 `capturedCount` 是"**我方被吃数**"还是"**我方吃掉的对方数**"。这是**极易搞反**的命名歧义：`me.capturedCount` 字面上像"我捕获了 N 个"，但**官方实现是"我方已损失数"**（`harness.js` 第 127 行）：

```js
const me = { side, pieces: myPieces, capturedCount: 6 - myPieces.length };
```

即 `capturedCount = 被吃掉的子数`。

**危害**：低但阴险——搞反会**完全颠倒**子力判断（把自己的损失当成收获），是"代码跑得通但棋力反向"的隐蔽 bug。

**建议**：改名为 `lostCount` / `capturedByOpponent`，或在文档中加粗注明"`capturedCount` = **我方已被吃掉的子数**"。

# 第二部分：游戏规则与机制的设计问题

## 2.1【高危】先手优势过强，且与「终局按子力裁定」叠加后削弱了棋力的区分度

这是一条**经过多组实验反复验证**的结构性问题，本次分析中影响最大的机制缺陷。

### 证据链

**（a）"连续无吃子按子力裁定"使对局大量以结算收场**【已证实】

本地复刻引擎仿真（双方均为官方随机棋手，N=400）：
```
material（20 ply 无吃子后按子力裁） : 217 场  ← 54.3%
eliminated（吃光）            : 113 场  ← 28.3%
draw（子力相等）              :  70 场  ← 17.5%
平均对局长度                  : 49.0 ply
```

真实线上回放（14 份，558 手）：
```
eliminated: 9 / 14
material:   2 / 14
draw:       3 / 14
```

线上本人 20 场正式对局【已证实】：**85%（17/20）以 `noCapture` 结算收场**，平均 82.7 手；终局平均剩 **17.8 / 32 颗子**、**59.9 / 104 点真实子力**。也就是说——**大半的棋子从未参与决定胜负**。

**（b）先手（黑）在等强度下决定性**【已证实，本地仿真】

```
强手 D4 vs 强手 D4（同一份代码，200 局）：
  黑胜 0 / 红胜 0 / 和 200
```

**全部 200 局都是和棋**。这个结果本身极有信息量：同一份深度 4 的确定性搜索自对弈下，**先手无法把初手优势转化为胜势**，双方互相抵消到子力完全相等。

而更强的对照（预算不对称实验，本人 v5 阶段，`budget.js`）：
```
黑 320ms  vs 红 2500ms  →  红 7 胜 0 负 1 和
黑 2500ms vs 红 320ms   →  红 7 胜 0 负 1 和
```
**两侧都是"深的一方通吃"**——说明**先手劣势可以被约 8× 的搜索预算完全逆转**，先手本身在均势下是**负资产**（黑方先动意味着先暴露、先送出可被利用的形态）。

**（c）开局随机性直接决定结果**【已证实，本人线上分组复盘】

把 v5（线上 v5，hash `3b9c835fd9c69a07`）的每一局按第 1 手分组，发现**完全相关**：
```
我执黑：开 (0,2)->(1,2)  →  7 胜 0 和
        开 (3,2)->(2,2)  →  0 胜 3 和（3 局全和）
我执红：应 (1,0)->(1,1)  →  2 胜 0 和
        应 (3,1)->(2,1)  →  0 胜 5 和
```
两个着法是**镜像等价**（4×4 棋盘上下左右对称 + 评估函数亦对称 → 两着法评估值**精确相等**）→ 由根层洗牌（`game.random`）**随机**决定走哪条 → **同一份代码随机产出胜或和**。

v6 用"规范序 tie-break"（`n 降 → h 降 → from 升 → to 升`）消除随机抖动后，**10 场计分挑战 10 战全胜且全部 4:0**，结果完全稳定。

### 问题分析

1. **胜负的方差来源不是"棋力"，而是"开局选点 + 骰子"**。当两条等价着法一条通向 7 胜、一条通向 3 和时，机制实际上把**一半的结果交给了随机数**。这直接削弱天梯排名的信噪比。
2. **结算制奖励"藏"而非"战"**。棋盘只有 16 格、双方各 6 子，中盘极易被填满；而吃子要求"恰好 3 子相连"，导致**棋子越少、可吃机会越稀**。终局时平均 17.8 子仍在场，说明"低烈度空转"是**占优策略**而非失误。
3. **先手在均势下是劣势**。这本身不是问题（许多棋类如此），但与"20 ply 无吃子即按子力裁定"叠加后产生恶性循环：**先手想避免劣势 → 越不敢交战 → 越容易触发结算 → 结算又完全比子力（先手没赚到净子力）→ 结果趋向和棋**。200 局全和正是这个循环的极端表现。

### 建议

- **方案 A（改结算权重）**：把 `material` 裁定的判据从"剩余子力总和"改为"**已吃子数**"或"**已吃子力价值**"。这样"主动进攻"直接兑换为胜势，从根上消除"龟缩占优"。
- **方案 B（改判定阈值）**：降低 `ncm >= 20` 阈值（如 20 → 12），压缩"稳稳拖到结算"的空间，逼出中盘交锋。
- **方案 C（改开局）**：把 4×4 扩到 5×5（双方 6 子），或让中央 4 格在开局即有 1-2 子，以增加可吃形态的密度。
- **方案 D（最小改动）**：引入"**重复局面判负/判和**"（三次同一局面）以打击空转，这是零结构成本的一步。

## 2.2【中】「吃子归零 ncm」与「裁定钟」制造了**拒绝吃子**的病理激励

**机制描述**：`ncm` 在吃子时归零、无吃子时 +1，并在 `ncm >= 20` 时按子力裁定。

**问题分析**：
- 若你**领先 1 子**，那么"什么都不吃、连续 20 手空转"就是**直接取胜计划**；而"吃子"会**归零计数**、甚至可能把局面复杂化。
- 于是产生一个**病态激励**：领先方**故意避开吃子机会**；落后方**拼命制造吃子**以重置计数。
- 【已证实】本人 v6 的评估函数中，`裁定钟` 项的**上限被刻意设为 700（严格小于一颗子的 1000）**，正是为了**杜绝"为了保 ncm 而拒绝吃子"**——这从侧面印证了该激励的强度：**它需要被主动压制，否则 Agent 会自发学会"不进攻"。**

**危害**：中。它使"进攻"与"获胜"在某些局面下**方向相反**，是一种反直觉的机制负债。

**建议**：把"吃子归零"改为"**每次吃子只把 ncm 减半**"或"**吃子不归零，而是重置为 0 但不足 8 ply 内不得再次裁定**"，以保留"吃子能延长时间"的战术价值、同时不制造"拒绝吃子"的诱惑。方案 A（2.1）亦可一并解决本项。

## 2.3【中】`Rules.apply` 计点，但**自实现内核零成本**——计费模型的"公平性幻觉"

**指南原文**：
> **每手算力上限 = 100 思考点**：每调用一次 `Rules.apply` 扣 1 点……**点数保证胜负只取决于棋力、与机器快慢无关**。

**问题**：这个设计目标是好的，但它**未把"自实现规则内核"纳入计量**，导致约束形同虚设：

- 官方 `Rules.apply` 一次 = 1 点 → 每手最多 100 次推演；
- 但**自己写一套等价规则内核**（本棋规则极简单，100 行内可完整实现），推演 **10 万次也不耗 1 点**。
- 【已证实，本人实践】：自实现内核后，可在 320ms 内搜索到**深度 14**；而官方内置棋手受 100 点限制（≈100 次 apply）**只能搜到深度 2**。

**危害**：这条规则的**实际约束力为零**——它约束的是"老实人"。天梯上真正的对手全部是自实现内核（[已证实] 本人 `identify.js` 反查 bot 1 棋谱，判定其为"另一个自实现内核对弈脚本，深度不低"）。

**这是设计意图问题而非 bug**：如果平台想让"算力预算"成为真实约束，应该：
- **方案 A**：允许但不鼓励自实现内核，改为限制**总挂钟**（当前已在做，但未写进指南——见 1.5 的挂钟实测）；
- **方案 B**：让 `game.board` 只在调用 `Rules` 时可用（把棋盘封装成不可直接读的对象），强制走计量 API；
- **方案 C**：接受现状，把"自实现内核是合法且核心的优化手段"写进指南，把"100 点"作为"用官方 API 时的预算"来表述。

**至少应修正指南措辞**："点数保证胜负只取决于棋力、与机器快慢无关"是一句**过度承诺**——自实现内核下，胜负**恰恰取决于机器快慢**（预算不对称实验证明 8× 预算可通吃）。

## 2.4【低】烟雾测试只保证"可靠性"不保证"棋力"——但失败成本不对称

**指南原文**：
> 只会输棋（eliminated/material/stalemate/draw）不拦截——烟雾测试只保证可靠性，不保证棋力。

**评价**：表述**清晰诚实**，且"失败不占版本号、修复后直接重提"的机制很友好。

**问题**：一处**未说明的性能陷阱**【已证实，本人 v3 事故】：
- 烟雾测试是**同步跑完 6 局**，因此**提交请求的耗时会随你的单步预算线性放大**。
- v2 配置（300ms/手）→ 烟雾请求耗时 **11.7s**；v3 配置（700ms/手）→ **约 9.1s 处触发 runtime 判负**（因为挂钟是每局累计，见 1.5）。
- 指南未提示"**单步预算过大 → 单局累计挂钟超限 → runtime 负**"这条因果链，作者可能在本地测"每手都很快"却仍在线失败。

**建议**：在指南中补充"每局累计挂钟"的实测口径（哪怕只说"单局累计约 10 秒级"），并把"烟雾测试是同步 6 局"写出来，提示作者控制单步预算。

## 2.5【低】3 名烟雾对手强度过低，通过烟雾 ≠ 能打天梯

**问题**：烟雾测试对手为官方三名训练棋手（牧童=随机 / 石郎=贪吃 / 棋圣=2 层子力）【已证实，`builtin-bots.js`】。其中最强的"棋圣"只有**深度 2 的纯子力搜索**，而天梯上的真实对手是**自实现内核、深度 10+** 的脚本。

**危害**：低（不构成阻塞），但它造成一个**认知陷阱**：作者容易把"烟雾通过 + 本地对训练棋手 100% 胜"误读为"我的棋力没问题"。本人 v1 阶段正是如此——**对官方训练棋手 100% 胜、0 故障**，但上线首战 **1:3 负于 bot 1**。

**建议**：在指南中明确"烟雾对手强度 ≈ 入门级；通过烟雾只证明可靠性，不证明棋力"，并建议作者**用公开回放反查对手强度**（这是本次最有价值的方法论，见第四部分）。

# 第四部分：给不同读者的行动建议

## 给 Agent 作者（最实用）

1. **不要依赖指南示例理解吃子**——直接照官方内核的**两种形态**写：`(己,己,敌)` 吃敌末位、`(敌,己,己)` 吃敌首位，**其余形态均不吃**。指南的"送上门不吃"示例**理由给错了**（内核只按颜色序列判定，不存在"送上门"这条规则）。
2. **自己实现规则内核，不要用 `Rules.apply` 搜索**。100 点只够深度 2，自实现内核可深到 14——这是天梯上唯一的真实杠杆（本人 v5→v6 的全部提升都来自此）。
3. **收官按"20 ply"而非"20 回合"计时**（= 10 个完整回合）。领先时约 10 回合前就要开始规避吃子；落后时要在 10 回合内制造吃子。
4. **控制单步预算并盯住"每局累计挂钟"**：单步 300-600ms 安全，700ms 无护栏会在 ~9s 处判 runtime 负。
5. **用公开回放反查规则与对手**：`GET /api/match/{urlId}` 返回 `initialBoard` + 逐手 `history`，是本平台**最高效的权威数据源**（本人据此建立的校验器在 1057 手上 0 处不符）。
6. **消除根层等价着法的随机抖动**（规范序 tie-break）——镜像等价的开局着法会成为"胜负骰子"。
7. **注意 `me.capturedCount` 是"我方损失数"**，不是"我方战果"。

## 给平台 / 规则设计者

1. **零成本高收益**：修正 1.1（吃子示例）、1.2（pass 契约）、1.4（改"手"）、1.5（挂钟口径与计分单位）、1.8（`capturedCount` 命名）——纯文档修正，不影响已发布代码。
2. **认真评估 2.1**（先手劣势 + 结算制导致 200 局全和、开局选点决定胜负）。建议优先试 **方案 D（重复局面判和/判负）**，改动最小；若追求观赏性则上 **方案 A（改用已吃子力裁定）**。
3. **重新表述 2.3 的算力约束**：当前"100 点保证与机器快慢无关"对自实现内核无效，属过度承诺。要么在技术上封死（封装 board），要么在文档上如实说明。
4. **补一句烟雾对手强度提示（2.5）**，避免作者把"通过烟雾"误读为"棋力达标"。
