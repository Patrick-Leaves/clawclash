# 邮箱验证注册设计 v1.0

> 状态：设计已确认（2026-09-03）。本文档是「邮箱验证码注册」功能的唯一设计来源，不含运行代码。

## 1. 背景与目标

当前平台的注册为「表单直建号」：`POST /api/account/register` 校验后立即创建 `accounts` 记录并下发会话 Cookie；邮箱验证为链接式（`EMAIL_VERIFICATION=on` 时发带 HMAC token 的链接，点击 `GET /api/account/verify` 置已验证），且默认关闭、邮件发送仅为控制台日志（TODO 接 SMTP）。

本次改为**验证码式邮箱验证注册**：用户填昵称 + 邮箱 + 密码 → 平台向邮箱发送 6 位验证码 → 用户回填验证码 → 核验通过**才创建账号**并发会话 Cookie。核心变化：

1. **建号时机后移**：核验通过前不建 `accounts`，改存 `pending_registrations` 暂存表。
2. **发送真实邮件**：手写极简 SMTP 客户端（`node:net` / `node:tls`，保持零第三方依赖），复用自有邮箱（QQ/163/企业邮箱）SMTP 授权码发信。
3. **旧链接式验证流程整体删除**（验证码流程天然覆盖，且「验证通过才建号」后不存在未验证账号）。

## 2. 已确认的需求决策

| 决策点 | 结论 |
|---|---|
| 邮件渠道 | 自有邮箱 SMTP，手写客户端（零依赖），不支持服务商 HTTP API |
| 注册表单 | 保留昵称（昵称 + 邮箱 + 密码 + 验证码） |
| 建号时机 | 验证码核验通过后才创建账号（pending 表暂存） |
| 验证码规格 | 6 位数字，10 分钟过期，最多 5 次错误尝试（超限作废需重发） |
| 重发冷却 | 每邮箱 60 秒 |
| 发信限额 | 每收件邮箱 3 封/天；每来源 IP 10 封/天；全平台上限环境变量可配（默认 200，0 = 不限），超出提示「今日注册名额已满，请明日再试」 |
| 旧链接式验证 | 整体删除（verify 端点、resend-verification、启动补齐、EMAIL_VERIFICATION 开关） |
| 文档位置 | 本文档（`GameDesign/`） |

## 3. 流程时序

```
用户（前端弹窗第 1 步）          平台                      SMTP 服务商
      │ 填昵称/邮箱/密码
      │ POST /api/account/register ──────────────▶
      │                           校验 + 查重(accounts)
      │                           生成 6 位验证码 → 哈希
      │                           upsert pending_registrations
      │                           三层限额检查通过后发邮件 ──────────▶
      │ ◀── 200 { emailMasked, expiresInSec, devCode? }（不发会话 Cookie）
      │（弹窗切第 2 步，显示已发送 + 60s 倒计时）
      │ 填验证码（可重发/更换邮箱）
      │ POST /api/account/verify-code ───────────▶
      │                           查 pending：过期→410 / 作废→410
      │                           比对 code_hash；错 → attempts+1（≥5 作废）
      │                           通过 → 事务内建 accounts(email_verified=1)
      │                                   + 删 pending + 终查昵称/邮箱占用
      │ ◀── 201 { accountId, nickname } + Set-Cookie 会话
      │（关弹窗、refreshMe、跳「我的」）
```

「更换邮箱」返回第 1 步修改后重新提交 = 重新注册（同邮箱 upsert 覆盖旧 pending、重置验证码与尝试次数）。

## 4. 数据层（db.js）

新增表（幂等建表，随启动迁移）：

```sql
CREATE TABLE IF NOT EXISTS pending_registrations (
  email          TEXT PRIMARY KEY,   -- 主键：同邮箱重注册覆盖旧 pending
  nickname       TEXT NOT NULL,
  password_hash  TEXT NOT NULL,
  code_hash      TEXT NOT NULL,      -- 验证码 scrypt 哈希（复用 auth.hashPassword），不存明文
  attempts       INTEGER NOT NULL DEFAULT 0,
  expires_at     INTEGER NOT NULL,
  created_at     INTEGER NOT NULL
);
```

db 层新增方法：

| 方法 | 说明 |
|---|---|
| `createPendingRegistration({nickname, email, passwordHash, codeHash, ttlMs})` | `INSERT OR REPLACE`（覆盖 = 重置验证码与 attempts） |
| `getPendingRegistration(email)` | 读取 pending（含 code_hash / attempts / expires_at） |
| `incrementPendingAttempts(email)` | attempts+1；达到 5 时删除该行并返回「作废」 |
| `deletePendingRegistration(email)` | 删除 |
| `finalizeRegistration(email)` | **事务内**：读 pending → 终查 nickname/email 是否已被 `accounts` 占用 → 插入 accounts（`email_verified=1`）→ 删 pending；冲突返回 `{ conflict: 'nickname' \| 'email' }` |
| `cleanupExpiredPendings()` | 启动时删除过期 pending（幂等；过期行无害，仅做卫生清理） |

`accounts` 表结构不变；`email_verified` 列保留但新账号恒为 1，基于它的拦截逻辑（若存在）随旧流程删除。`setEmailVerified` / `markAllAccountsVerified` 删除。

## 5. API 契约（server.js）

### 5.1 改造：`POST /api/account/register`

body `{ nickname, email, password }`，流程：

1. 频控 `reg:<ip>` 5 次/10 分钟（沿用现状）
2. 字段校验（沿用现状：必填、邮箱正则、密码 8–256 位）
3. 查重 `accounts`（昵称/邮箱占用 → 409 + `field`，沿用现状）
4. 生成 6 位验证码（`crypto.randomInt`）→ `auth.hashPassword(code)` 存 `code_hash`
5. `createPendingRegistration`（upsert，TTL 10 分钟）
6. 三层发信限额检查（见 §6），超限 429
7. 发送邮件（见 §7）；SMTP 已配置但发送失败 → **502**（pending 保留，用户可重试注册覆盖重发；验证码不回传）
8. 响应 `200 { ok:true, emailMasked, expiresInSec:600 }`；SMTP 未配置的降级模式下额外带 `devCode`（仅非生产环境）

**不再创建账号、不再下发会话 Cookie。** 邮箱掩码示例：`p***@qq.com`（首字符 + `***` + `@` 之后部分）。

### 5.2 新增：`POST /api/account/verify-code`

body `{ email, code }`：

| 场景 | 响应 |
|---|---|
| 参数缺失 / 格式不符 | 400 |
| 无 pending 记录 | 404「请先发起注册」 |
| 已过期 | 410 `{ reason:'expired' }`「验证码已过期，请重新获取」 |
| 已作废（错 5 次） | 410 `{ reason:'exhausted' }`「尝试次数过多，请重新获取」 |
| 验证码错误 | 400 `{ remaining }`（remaining = 5 − 已用次数） |
| 昵称/邮箱在 pending 期间被他人占用 | 409 + `field`（前端引导回第 1 步改名重提） |
| 核验成功 | **201** `{ ok, accountId, nickname }` + `Set-Cookie` 会话 |

核验频控：`verify:code:<email>` 与 `verify:code:<ip>` 各 10 次/10 分钟（防撞库）。

### 5.3 新增：`POST /api/account/resend-code`

body `{ email }`：重新生成验证码（upsert 覆盖）、重置 attempts、重发邮件。受 §6 三层限额 + 60s 冷却约束。无 pending 记录 → 404「请先发起注册」；限额/冷却超限 → 429。响应 `200 { ok, expiresInSec, devCode? }`。

### 5.4 删除项

| 删除 | 位置 |
|---|---|
| `GET /api/account/verify` 链接验证端点 | server.js |
| `POST /api/account/resend-verification` | server.js |
| 启动「历史未验证账号补齐」块 + `EMAIL_VERIFICATION` 常量 | server.js |
| `makeVerifyToken` / `verifyVerifyToken` | auth.js（验证码走 DB 哈希，无需签名 token） |
| `sendVerificationEmail`（链接版） | server.js |
| `setEmailVerified` / `markAllAccountsVerified` | db.js |
| 前端 `showVerifyLink` 与链接弹窗逻辑 | public/platform.js |

## 6. 发信限额（三层，复用 ratelimit.js 滑动窗口）

| 层 | 键 | 额度 | 超限响应 |
|---|---|---|---|
| 每收件邮箱 | `verify:send:<email>` | 3 封/天 | 429「该邮箱今日验证码次数已达上限，请明日再试」 |
| 每来源 IP | `verify:send:<ip>` | 10 封/天 | 429 同上 |
| 全平台 | `verify:send:global` | `SMTP_DAILY_MAX`（默认 200，0 = 不限） | 429「今日注册名额已满，请明日再试」 |

- 重发冷却：`verify:resend:<email>` 1 次/60 秒。
- 三层限额在**发信前**检查；全平台层保护 SMTP 服务商发信额度不被刷光（QQ 免费额度仅数百封/天）。

## 7. SMTP 客户端（新文件 platform/mail.js，零依赖）

手写极简 SMTP 客户端，仅用 `node:net` + `node:tls` + `crypto`：

- **连接模式**：`SMTP_SECURE=true` → 直连 465 隐式 TLS（`tls.connect`）；`false` → 587 明文连接后 STARTTLS 升级（EHLO 探测能力；不提供明文中继）。
- **会话流程**：EHLO → STARTTLS(可选) → EHLO → AUTH LOGIN（base64 用户名/密码）→ MAIL FROM → RCPT TO → DATA → QUIT。
- **DATA 段**：主题 `=?UTF-8?B?...?=` 编码（中文）；正文 UTF-8 + `Content-Transfer-Encoding: base64`（规避 dot-stuffing 与行长限制的编码坑；行首 `.` 转 `..` 仍做防御性处理）。
- **超时**：连接与每步命令 15 秒（socket timeout），异常/超时即销毁 socket 并报错。
- **配置**（环境变量）：`SMTP_HOST` / `SMTP_PORT` / `SMTP_SECURE` / `SMTP_USER` / `SMTP_PASS` / `SMTP_FROM`。
- **降级**：`SMTP_HOST` 未配置 → 不真发信，日志打印验证码，非生产环境响应带 `devCode`（沿用现有 devExposed 思路，演示可用）。
- **邮件内容**：主题「【Claw Clash】邮箱验证码」；正文含 6 位验证码、10 分钟有效期提示、防钓鱼提醒（平台不会索取密码）。
- 发送失败时**验证码不回传前端**（防验证码泄漏），接口报 502。

## 8. 前端交互（public/fragments/shared_modals.html + public/platform.js）

注册弹窗改两步（同一弹窗内切换，不关窗）：

- **第 1 步**：现有表单（昵称/邮箱/密码/确认密码 + 实时校验），提交后不关弹窗，切第 2 步。
- **第 2 步**：显示「验证码已发送至 `emailMasked`」；验证码输入（`inputmode="numeric"`，6 位，自动聚焦）；60s 重发倒计时（结束后可点重发）；「更换邮箱」返回第 1 步（预填原值）。
- **提交核验**：201 → 关弹窗 → `refreshMe()` → 跳当前游戏「我的」页（沿用现有成功路径）。
- **错误映射**：400 验证码错误 → 显示剩余次数；410 → 引导点重发；409 → 返回第 1 步并标出冲突字段；429 → 展示限额文案。
- **dev 降级**：响应带 `devCode` 时自动填入验证码框（演示环境免查日志）。

## 9. 安全要点

- 验证码**只存 scrypt 哈希**（`auth.hashPassword` 复用），DB 拖库不可直读；核验走 `verifyPassword`（timingSafeEqual）。
- 验证码低熵（10⁶），配合 5 次尝试封顶 + 核验频控 + 60s 重发冷却 + 三层发信限额共同兜底。
- 生产环境**绝不**打印验证码、绝不回传 `devCode`（降级模式仅非生产）。
- 核验成功建号在**事务内**完成（建号 + 删 pending 原子）；昵称/邮箱在事务内终查，杜绝 pending 期间抢注竞态。
- 注册接口不再发会话 Cookie（核验前无登录态）；会话 Cookie 属性不变（HttpOnly / SameSite=Lax / 生产 Secure）。
- 密码哈希复用现有 scrypt 加盐；登录接口防超长密码 scrypt DoS 的短路逻辑保持不变。

## 11. 上线准备清单（运营侧需要准备的）

1. **邮箱账号与授权码**：QQ 邮箱（设置 → 账户 → 开启 SMTP → 生成 16 位授权码）或 163（开启 POP3/SMTP → 客户端授权密码）或企业邮箱（管理员开启 SMTP）。建议使用**专门发信账号**，不用个人主邮箱。
2. **端口**：465（隐式 TLS，`SMTP_SECURE=true`）或 587（STARTTLS，`SMTP_SECURE=false`）。中国大陆家宽 25 端口被封，不可用。
3. **环境变量**（启动时注入，项目零依赖无 dotenv）：

   ```
   SMTP_HOST / SMTP_PORT / SMTP_SECURE / SMTP_USER / SMTP_PASS / SMTP_FROM
   SMTP_DAILY_MAX   # 全平台每日发信上限，默认 200，0 = 不限
   ```

4. **服务商发信限额**：QQ 免费 SMTP 有每日上限与频率限制，个人平台够用；如预计注册量大，改用企业邮箱或调低预期。
5. **测试验证**：改环境变量后跑 `npm test`；本地演示可不配 SMTP（自动降级 dev 模式）。

## 12. 范围外（本期不做）

- 引入 nodemailer 等第三方依赖（违背零依赖原则）
