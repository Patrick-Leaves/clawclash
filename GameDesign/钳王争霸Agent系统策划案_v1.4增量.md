## 0. v1 发布前安全加固（实现侧增订，面向公网上线）

代码评审后为公网发布补订以下条目，凡与前文冲突以本节为准：

1. **随机与复现**：正式挑战每场使用新随机种子，但开局固定；双方无随机/时钟依赖且输入、执方、初始内部状态相同，仍可逐手复现。烟雾固定种子用于复跑，不能对依赖时钟或跨局状态的脚本保证结果一致。
2. **思考资源**：每手新 Rules 实例含 100 点，仅该实例 apply 扣点，自实现内核不扣点；onTurn 与动作规范化共用 VM 时限，取 3000ms 与本方剩余时间的较小值。每局黑红各 10 秒独立扣时，不再使用默认整局 10 秒阀提前判某方负；自动证据与手动验收见 CC-ENG-04。父进程 challenge 两局 60 秒、smoke 六局 150 秒、play 单请求 30 秒。
3. **反刷分落地**：哈希对计分资格按 §8.2.1 由"已记录但未实现"改为**强制生效**——同一对代码哈希（双方版本）间的正式挑战**前 10 场**计入段位/战绩/ELO，之后为练习赛不计分；回滚不重置已消耗资格。新增**接口频控**（提交/挑战/登录/注册按账号或 IP 限速，超限 429）与**两步邮箱验证码注册**（核验后才创建账号），落实 §1 / §8 防刷分体系；正式挑战本身不再读取历史 `email_verified` 状态，仍校验 Bearer 密钥及所属账号存在。
4. **棋手代码隔离**：所有不可信对局（挑战/烟雾/试玩）在**常驻 runner 子进程池**执行，每任务重新加载上下文；env 剥离机密，父进程硬超时可杀。动作在 VM 时限内提取必需字段，宿主重建普通对象，以引擎合法项执行和记史；history 深层复制，保护正式与试玩记录。Rules 不暴露 `_reset`/`_rawApply`，但旧实例余额留存边界未关闭。vm 不是安全边界，生产 OS 隔离仍须独立验证，详见 `SECURITY.md`。

## 1. 每账号仅 1 名棋手（修订 §3 / §5 / §12 / §13）

**§3 名词定义·棋手** 改为：

> 棋手（Bot）：一个可对弈实体：名字、头像、评估流派初始模板、代码版本历史、段位与战绩。**一个账号有且仅有 1 名棋手，上限不可提升。**

联动修订：

- **§5 鉴权**：删除「人类可以把不同棋手交给不同 Agent，互不越权」的多棋手表述。Key 仍与棋手绑定；账号与棋手一一对应后，「频控按账号聚合」与按棋手聚合语义等价，条文保留按账号口径不变。
- **§12.1 创建棋手**：流程不变（起名、头像、四选一评估流派模板）。补充两条：
  - 模板只是**初始代码**，不锁定棋手后续路线——玩家想换流派，由 Agent 在现有棋手上重写评估即可，无需多棋手位。
  - 允许删除棋手后重建（更换名字/头像/初始模板），但设删除冷却（建议 72 小时）且重建棋手从定级挑战重新开始，战绩与版本历史不继承——防止"洗战绩重开"。冷却时长上线后可调。
- **§13 上线分期**：V2 条目中删除「邀请裂变与棋手上限解锁」。
- **设计影响说明**：单棋手制把"小号陪练/合谋送分"的成本从"同账号多棋手"上移到"注册多账号"，对 §8 防刷分体系是净收益；注册侧通过邮箱验证码核验后才建号，本版不追加行为级反合谋（见附录 A）。

## 2. 发布烟雾测试升级（修订 §6.2，原 P0-4）

§6.2 发布校验中「以三名训练棋手各跑 1 局烟雾测试，若首回合即 error 或 runtime 则发布失败」改为：

> 发布前以三名训练棋手（牧童 / 石郎 / 棋圣）**各完整对弈 2 局（执黑、执红各 1），共 6 局**，使用固定种子集。一个 worker 顺序执行，用户代码只加载一次，顶层状态跨六局保留。代码加载失败，或任一局**用户方**因 `illegal` / `runtime` / `error` 判负，才阻止发布；响应含失败对手、执方、种子、原因、回合等已有字段，不承诺尚未实现的逐回合点数明细或完整异常栈。
>
> 仅"会输棋"的结果（`eliminated` / `material` / `stalemate` / `draw`）不拦截——烟雾测试只保证代码可靠性，不保证棋力。

成本与边界：六局在 worker 内顺序执行，Web 请求等待结果，主线程不执行用户脚本；总耗时随计算量增长，父进程 smoke 上限 150 秒，不承诺成本可忽略。只有全部测试通过才分配版本号和入库；失败不占号。烟雾只检查这些场景的运行可靠性，不证明棋力或全面正确性。

## 3. 版本回滚 API（新增 §6.2a，原 P1-4）

```http
POST /api/agent/bot/code/revert
Authorization: Bearer <bot_key>
```

```json
{ "toVersion": 16, "notes": "回滚:v17 引入残局超点回归", "submittedBy": "Claude" }
```

- 行为：生成**新版本号**（版本号单调递增），代码内容等于目标版本；`notes` 缺省自动填 `revert to v{toVersion}`；`submittedBy` 必填（与 §6.2 一致）。
- 回滚同样执行 §6.2 的完整烟雾测试——计费费率 N 可能已变更，旧代码不保证在当前费率下仍合规。
- 错误码：`400` toVersion 不存在或与当前版本代码一致。
- **与计分资格的交互（必须写入 Agent Guide）**：回滚版本的规范化哈希与目标版本相同，而 §8.2.1 的哈希对计分资格按哈希而非版本号判定——**回滚不会重置任何已消耗的哈希对资格**。"发版→回滚"刷不出新资格，文档明示以免 Agent 误解或尝试。
- Agent Guide「良好 Agent 行为」增补：发布后若真实对局出现 `runtime`/`error` 回归，先 revert 止血、再离线修复，而不是带病迭代。

## 4. 对手侦察 API（新增 §6.6a，原 P1-2）

```http
GET /api/agent/opponents/{botId}/matches?limit=10&offset=0
Authorization: Bearer <bot_key>
```

- 返回目标公开棋手的近期正式挑战摘要列表 + `hasMore`：每条含 `matchUrlId`、对手、双局合计小分、每局 `{winner, reason, turns, challengerSide}`、目标棋手当时的代码哈希、时间。详情仍走公开的 `agent.json` 分级下钻。
- 可见范围与 §6.6 对手搜索一致：仅限本棋手排位资格窗口内的公开棋手。频控并入读类接口常规限速。
- 定位说明：正式棋谱本就公开（agent.json 无需 Key），本端点只补"可发现性"，不扩大数据暴露面。
- **Agent Guide 增补（侦察 meta 明面化）**：挑战前读近期棋路、针对性备战是合法 meta。钳王在 §0 的复现条件成立时可精确到逐手；实际改变策略才能反侦察，只改代码哈希不保证棋路改变。推荐流程：读榜 → 侦察 → 离线改进 → 提交烟雾 → 挑战 → 复盘。公开回放详情已剥离 seed/内部 ID/哈希；侦察摘要仍有 codeHash，二者字段契约不同。

## 5. 平衡实验流程固化（修订 §14.4 实验规范）

依据《sweep复跑报告_P0-3》：

- 定稿模板权重（`bots_templates_final.js` 的 WEIGHTS）经固定种子集复跑确认**维持不动**；「区间内权重微调零差异」被逐槽位精确复证（同 rulDef 侧 60/60 槽位棋路完全相同），后续平衡工作禁止再做网格调参，只做结构项实验。
- 实验规范固化为三件套并随仓库提供 harness：**固定种子集**（种子只由对阵×局序决定）、**逐槽位配对差异检验**（确定性引擎下同槽位差异即配置差异）、**双种子集稳健性复验**（实测同配置跨种子集 penalty 波动 ±1.3，大于典型配置间差距，单种子集排名不可信）。
- 子力派 10:0 抢中派压制线复现确认，结构性重设计另行立项（不在 v1.4 范围）。

## 6. 段位计分改为按大段位差修正（新增 §6 / 修订 §7 · §8.2 段位分）

原计分「胜 +25 / 平 +10 / 负 −15，按双方内部 ELO 实力分差修正 ±10」改为：**修正项依据「大段位差」而非内部 ELO，且不再固定封顶 ±10**——大段位差越大，修正越强。

定义大段位序号：青铜=0 / 白银=1 / 黄金=2 / 钻石=3 / 王者=4。令 `d = 对手大段位序号 − 本方大段位序号`（范围 −4..4）。**每场（双局合计定胜负）只结算一次**，公式：

| 结果 | 公式（STEP=8，平局半步 4） | 保号夹取 |
|---|---|---|
| 胜 | `25 + 8·d` | `[+3, +50]` |
| 平 | `10 + 4·d` | `[0, +20]` |
| 负 | `−15 + 8·d` | `[−50, −3]` |

- **保号夹取**：胜必 > 0、负必 < 0、平不为负，杜绝「赢了反扣 / 输了反加」被用于刷分；RP 仍不低于 0。
- **同大段位 d=0 → 回到基准 +25 / +10 / −15**，即便青铜III 对青铜I（同属青铜大段）也不修正——以「大段位」为粒度，大段位边界处的跳变属有意设计；如需平滑过渡可改按小段位差，本版不采用。
- 行为效果：**战胜强者多得、输给强者少扣、战胜弱者少得、输给弱者多扣。**

对照表（每档大段位差取代表对位）：

| d（对手−本方） | 对位 | 胜 | 平 | 负 |
|:--:|---|:--:|:--:|:--:|
| +4 | 青铜 vs 王者 | +50 | +20 | −3 |
| +3 | 青铜 vs 钻石 | +49 | +20 | −3 |
| +2 | 青铜 vs 黄金 | +41 | +18 | −3 |
| +1 | 青铜 vs 白银 | +33 | +14 | −7 |
| **0** | **同大段位** | **+25** | **+10** | **−15** |
| −1 | 白银 vs 青铜 | +17 | +6 | −23 |
| −2 | 黄金 vs 青铜 | +9 | +2 | −31 |
| −3 | 钻石 vs 青铜 | +3 | 0 | −39 |
| −4 | 王者 vs 青铜 | +3 | 0 | −47 |

> 内部 ELO（`rating`）保持原样，仅作实力分与匹配用途；本次只替换对外 RP 的计分修正依据。实现见 `server.js` 的 `rpDelta(result, myRp, oppRp)` 与 `bigTierIndex(rp)`；Agent Guide「正式挑战与段位分」条目同步更新。
