# 注册页垃圾邮件提示 · Spec v1.0

> 日期：2026-09-20
> 状态：已确认，待实现
> 相关：[邮箱验证码注册_Spec_v1.1](邮箱验证码注册_Spec_v1.1.md)

---

## 一、背景

平台唯一的注册入口是邮箱验证码。上线前的送达率验收（AC22）结果：

| 收件域 | 结果 |
|---|---|
| 163 | ✅ 送达收件箱 |
| QQ | ✅ 送达收件箱 |
| hotmail | ✅ 送达收件箱 |
| Gmail | 未测（主动放弃） |

三个域全部落在收件箱，但这不代表万事大吉：**验证码邮件被收件方判为垃圾邮件是行业常态**，且随发信量增长、收件方风控策略变化而波动。一旦发生，用户的体感是「点了发送验证码，然后什么也没发生」——他不会想到去翻垃圾箱，只会认为网站坏了，然后离开。

**这不是可选的体验优化，而是注册漏斗的兜底。** 因此在界面上主动告知，成本极低、收益明确。

## 二、目标

用户在等待验证码时，能直接在界面上看到「去哪里找」和「找到后做什么」，无需客服介入。

非目标（明确不做）：

- 不做「重新发送」之外的重试机制——已有重发按钮，无需叠加
- 不做倒计时结束后才出现的延时提示——需要它的人一开始就在找
- 不显示发件人邮箱地址——运营方使用个人邮箱，公开在注册页等于泄露；用户找到邮件后自然能看到发件人
- 不做发送失败时的提示——那是另一套既有逻辑（`registrationError()`），本次不碰

## 三、设计

### 3.1 位置

注册弹窗是两步的：第一步填资料并点「获取验证码」，成功后背 `showAuthPanel('verify')` 切到第二步。

**提示放在第二步**，因为第一步在点击成功的瞬间就被替换掉了——放在那里用户根本看不到。第二步是用户盯着等邮件的界面，且点「重新发送验证码」后依然停留在这里，提示持续有效。

### 3.2 界面

```
┌──────────────────────────────────┐
│  验证邮箱                     ✕  │
│                                  │
│  第 2 步 · 验证码已发送至        │
│  z***@163.com                    │
│                                  │
│  六位验证码                      │
│  ┌────────────────────────────┐  │
│  │  000000                    │  │
│  └────────────────────────────┘  │
│  验证码 9:58 后失效   47 秒后可重发│
│                                  │
│  💡 没收到？请到「垃圾邮件」文件夹│  ← 新增
│     找找，并把它标记为「非垃圾邮件」│
│                                  │
│  ┌────────────────────────────┐  │
│  │        验证并注册          │  │
│  └────────────────────────────┘  │
│  ┌────────────────────────────┐  │
│  │      重新发送验证码        │  │
│  └────────────────────────────┘  │
│                                  │
│  更换邮箱  ·  去登录             │
└──────────────────────────────────┘
```

**文案**：

> 💡 没收到？请到「垃圾邮件」文件夹找找，并把它标记为「非垃圾邮件」

选这句的理由：既说清「去哪里」（垃圾邮件文件夹），也给出「做什么」（标记为非垃圾邮件）。只说位置的话，用户翻到邮件、拿到验证码就关掉了，下一次同样的问题会再发生一遍。

「标记为非垃圾邮件」而非「加入白名单」，用词与各邮件客户端里的实际按钮一致，对非技术用户更可执行。

### 3.3 样式

复用站内已有的 `.hint` 工具类（`public/style.css:327`）：

```css
.hint { color:var(--muted); font-size:12px; margin:8px 0; display:flex; align-items:center; gap:6px; }
```

与「创建选手」弹窗里那段灰色说明文字同款，颜色、字号、间距与站内其他地方一致。

**刻意不用 `.warn-box`**（珊瑚色警告框）：邮件其实发送成功了，用警告样式会让用户误以为出错。

### 3.4 改动

**只改两个文件，不涉及任何 JavaScript 逻辑。**

`public/fragments/shared_modals.html` —— 在 `#authVerify` 面板内、`.verification-meta` 之后插入一行：

```html
<p class="hint" id="verifySpamHint"><span>💡</span><span>没收到？请到「垃圾邮件」文件夹找找，并把它标记为「非垃圾邮件」</span></p>
```

文字外层包 `<span>` 而非裸文本：`.hint` 是 flex 容器，裸文本会变成匿名 flex item，换行行为在各浏览器下不一致；包一层 span 让两行折行可预期。

`test/registration-ui.test.js` —— 加一条断言，锁住「该提示存在于第二步面板且文案含关键词」。纯静态文案没有行为可测，但这条断言能在日后重构弹窗时拦住误删。

### 3.5 为什么不需要改 JS

提示挂在 `#authVerify` 内部，而该面板的显示/隐藏已由 `showAuthPanel()` 统一管理：

- 发送验证码成功 → `showAuthPanel('verify')` → 面板出现，提示随之出现
- 点「更换邮箱」→ `returnToRegistration()` → 回到第一步，提示随之消失
- 重发成功 → 仍停在第二步，提示持续可见

**没有新状态、没有新分支、没有新事件监听。**

## 五、风险

| 风险 | 评估 |
|---|---|
| 文案占用两行，弹窗变高 | 低。弹窗本身留有余量；实现后以截图确认 |
| `.hint` 的 `margin:8px 0` 与上方 `.verification-meta` 的 `margin-bottom:12px` 叠加成 20px 间距 | 低。视觉上偏松但无碍；若明显不协调，可加一条作用域限定的样式微调，不改全局 `.hint` |
| 用户仍旧不看提示 | 无法完全避免，但把兜底放在用户视线必经之路上，已是最优解 |
