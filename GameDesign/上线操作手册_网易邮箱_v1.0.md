## 0. 总览

### 0.1 关键路径

**关键路径 = ICP 备案审核时钟（1–3 周）。**

上海轻量服务器上，未备案域名无法使用 80/443 端口（腾讯云接入侧阻断）。【外部】因此域名 + Nginx + HTTPS 完全卡在备案之后；而其余全部技术工作都可以在这 1–3 周里并行完成，实际动手量约 1–2 天。

> **结论：最快上线时间 = 备案通过日 + 半天。** 晚一天提交备案，上线就晚一天，与技术进度无关。

### 0.2 阶段与并行关系

```
第 1 天  ┌─ A. 提交 ICP 备案（第 1 节）────────────────┐  ← 长周期，先跑起来
         ├─ B. 网易邮箱开 SMTP + 拿授权码（第 2 节）    │  ← 已完成 ✅
         ├─ C. 实测 SMTP 提交路径（第 3 节）           │  ← ✅ 已确认通过，无需改代码
         └─ D. 服务器初始化（第 4 节）                 │
                                                       │
第 2 天  部署应用（第 5 节）→ 本机验证 + AC22 送达率验收  │
         （第 7 节）→ 安全加固（第 8 节）→ 公网临时验证  │
         （第 9 节）                                    │
                                                       │
等备案   域名 + Nginx + HTTPS + 切生产模式 + 上线验收 ←──┘
         （第 10–11 节）
```

> **顺序要点**：安全加固（第 8 节）排在公网临时验证（第 9 节）**之前**。因为一经开放公网，玩家脚本就有机会在未封锁出站的 runner 里执行——SECURITY.md 把网络出站隔离列为威胁模型的必做项【代码：SECURITY.md】。两个阶段可在同一天完成，别为了省十分钟把顺序颠倒。

### 0.3 三个可能挡住上线的点

| # | 阻塞点 | 性质 | 状态 |
|---|---|---|---|
| 1 | ~~网易 465 是否接受 `EHLO localhost`~~ | ~~唯一可能要改代码的项~~ | ✅ **已实测通过，无需改代码**（见第 3 节） |

## 1. 第 0 步：提交 ICP 备案（今天）

这是整个项目唯一的长周期项，**必须在第 1 天启动**，此后所有技术工作都在这段时间内并行。

## 2. 第 1 步：网易邮箱侧准备

### 2.1 确认邮箱类型

| 你注册的域名 | 登录地址 | SMTP 主机 | 备注 |
|---|---|---|---|
| `@163.com` | https://mail.163.com | `smtp.163.com` | |
| `@126.com` | https://mail.126.com | `smtp.126.com` | |
| 企业邮箱 | 企业邮入口 | `smtp.qiye.163.com` | 有独立的风控与限额策略 |

以上均为【外部】信息，以网易官方文档为准。

### 2.2 开启 SMTP 服务并获取授权码

1. 登录对应网页邮箱 → 顶部「设置」→「POP3/SMTP/IMAP」（或「邮箱设置 → 收取」）
2. 找到「SMTP服务」，状态若为「已关闭」则点「开启」
3. 按弹出提示用**绑定手机发送一条短信**完成验证
4. 页面显示 **16 位「客户端授权密码」——只显示这一次，立即复制保存** 【外部】
5. 若之前开过 SMTP 但授权码已忘，点「重置授权码」重新获取（重置后旧码立即失效）

> **这是整个流程中最常见的一号坑：授权码不是邮箱登录密码。** 填登录密码必然 `535` 认证失败。

### 2.3 先确认账号本身能发信

用网页邮箱手动给自己发一封信，确认该账号发信功能正常，再配置到平台。这一步排除掉「账号本身被限制」这个变量。

## 3. 第 2 步：实测 SMTP 提交路径

> ✅ **结论已确定（2026-09-20 实测）：网易接受 `EHLO localhost`，无需改代码。**
>
> 平台把 EHLO 名**硬编码成 `localhost`**【代码：`platform/mail.js:256`、`:267`】，且没有任何环境变量能覆盖它。曾担心网易 465 提交服务会拒收非 FQDN 的 EHLO——**实测证明不会**：用真实客户端连 `smtp.163.com:465`，连接、TLS 握手、`EHLO localhost`、`AUTH LOGIN` 四步全部被接受，流程一路走到认证阶段才因（故意填错的）凭据失败，返回 `smtp_535`。
>
> **因此这一步不再是阻塞项，也不需要任何代码改动。** 下面的命令保留下来供你自行复验或日后排查。

### 3.1 用项目自带工具做一次真实发信检查（推荐）

项目根目录下有一个 `smtp-check.js`，它调用平台**真正在用的那套发信代码**，完整走一遍「连接 → TLS → EHLO → 登录 → 投递」，测出来的就是上线后的真实行为。

```bash
node smtp-check.js
```

它会依次问三个问题（直接输入后回车即可，不需要任何编程知识）：

1. 你的完整 163 邮箱地址（如 `zhangsan@163.com`）
2. 你复制保存的那 16 位授权码
3. 收件邮箱（直接回车 = 发给你自己）

然后它会真的发一封信出去，并把结果翻译成中文告诉你。**成功的话请去收件箱（和垃圾箱）确认一下真的收到了**——这一步同时就把第 7.3 节的 AC22 送达验收做掉了一次。

### 3.2 手工复验（可选，用 openssl）

如果你想知道底层到底发生了什么：

```bash
openssl s_client -crlf -connect smtp.163.com:465 -servername smtp.163.com
```

连接建立后手打一行 `EHLO localhost`，预期回 `250` 开头的多行能力列表，其中含 `AUTH ... LOGIN`。

> 客户端对 `AUTH LOGIN` 也是硬要求，只认 `LOGIN` 机制、不认 `PLAIN`。【代码：`platform/mail.js:269-271`】实测网易宣告了 `LOGIN`。

### 3.3 证书链（已随 3.1 一并验证）

代码用严格证书校验（`rejectUnauthorized: true`）且最低 TLS 1.2。【代码：`platform/mail.js:221-230`】3.1 的检查能跑到认证阶段，就已经证明证书链在 Node 下校验通过。

单独复验的话：

```bash
timeout 30 node -e "const tls=require('tls');const s=tls.connect({host:'smtp.163.com',port:465,servername:'smtp.163.com',minVersion:'TLSv1.2'},()=>{console.log('OK',s.getPeerCertificate().subject.CN);s.end();});s.on('error',e=>{console.error('FAIL',e.message);process.exit(1);});"
```

### 3.4 IP「洗白」—— ⬜ **尚未完成（必须在服务器上做）**

上海轻量实例是新出口 IP，网易可能把首次 SMTP 登录判为异地异常（`554` 或要求短信验证）。【外部，网易不公开判定规则与封禁时长】

**注意：在本地电脑上跑通 3.1 不能替代这一步。** 本地网络和服务器是两个不同的出口 IP，网易分别对待。目前所有发信测试用的都是本地 IP，**服务器 IP 在网易眼里仍是完全陌生的**。

**做法**（服务器部署完成、`ecosystem.config.js` 配好之后）：

1. 在服务器上执行 `node smtp-check.js`，发一封到自己的邮箱，确认真的收到
2. 若返回 `554` 或要求验证，先用服务器的浏览器（或经服务器）登录一次网易网页端、完成短信安全验证，再重试
3. 确认能稳定发出后再开放注册

**但别把这一次成功当成永久结论**：服务器 IP 对网易而言是新地址，风控判定可能是渐进的——头几封通过、量上来后才被限。**上线后第一周要盯着发信失败率**，出现大量发信失败时按 12.4 暂停发码，而不是硬顶。

### 4.6 生成会话密钥


## 6. 网易邮箱配置取值表

| 变量 | 填什么 | 理由 |
|---|---|---|
| `SMTP_HOST` | `smtp.163.com`（126 则 `smtp.126.com`） | **只能写主机名。**含空白字符（空格/制表/换行）会判 `invalid_host` → 发码 503；写解析后的 IP 或尖括号**不会**被拦在这里，会在连接/TLS 证书阶段以传输错误失败【代码：`platform/mail.js:44`】。所以两种情况都要避开 |
| `SMTP_SECURE` | `true` | 走 465 隐式 TLS，是网易明确支持的路径，也是代码默认【代码：`platform/mail.js:35`】。**不要用 `false`**——代码在 `SMTP_SECURE=false` 时**强制 STARTTLS**，EHLO 能力里没有 STARTTLS 就直接抛错【代码：`platform/mail.js:257-258`】，而网易 587/STARTTLS 的支持情况资料互相矛盾【外部】 |
| `SMTP_PORT` | `465` | 与上面对应（`994` 也是网易的 SSL 端口，可作备选【外部】）。留空时代码在 secure=true 下默认 465，但显式写出更好排障【代码：`platform/mail.js:40`】 |
| `SMTP_USER` | 完整地址如 `yourname@163.com` | SMTP 认证账号，必须写全地址，不能只写 `@` 前的前缀 |
| `SMTP_PASS` | 16 位客户端授权密码 | 不是邮箱登录密码。代码原样 base64 后发送，不做任何变换【代码：`platform/mail.js:276`】 |
| `SMTP_FROM` | **整行删掉，不要设** | 163 要求发件人地址 = 认证账号，否则 `MAIL FROM` 被 `553/550` 拒【代码：`platform/mail.js:278` 裸拼 `MAIL FROM:<from>`】。不设时默认复用 `SMTP_USER`【代码：`platform/mail.js:50`】，从根上避免填错 |
| `SMTP_DAILY_MAX` | `40`（**不要用指南的 200**） | 见 6.1 |

### 6.1 为什么 `SMTP_DAILY_MAX` 要压到 40

平台的这条额度线**只在「被 SMTP 服务器接受（返回 250）」时计数**——发信失败不占额度。【代码：`platform/registration.js:217-229` 只在 `outcome === 'accepted'` 时 commit；`db.js:380-381` 只统计 `state='sent'`】

网易免费邮箱的真实日上限说法不一（官方口径 300–400 封，第三方普遍反馈约 50 封），【外部，无官方公开数值】且账号级风控是动态判定的。**如果平台配额设得高于网易的实际上限**，网易会先开始 5xx 拒绝，**平台的配额永远撞不到**，结果是对用户持续返回通用的发信失败，而永远不会给出受控的「当日额度已满」提示。

设 40 可以让平台在网易触发风控之前就自己先受控限流。若你的账号确认有更高额度再上调，但**必须 ≤ 网易真实上限**。

### 6.2 额度与节流一览

| 层级 | 平台限制 | 触发时的表现 |
|---|---|---|
| 每邮箱 | 3 封/日 | `429` |
| 每 IP | 10 封/日 | `429` |
| 全平台 | `SMTP_DAILY_MAX`（本次设 40） | `429 global_daily_limit` |
| **发码频率** | **同 IP 5 次 / 10 分钟**（`register` 与 `resend` 共用同一个桶） | `429 rate_limited` |
| 并发发信 | 同时最多 4 条 SMTP 连接 | `503 send_busy` |
| 冷却 | 成功发送后同邮箱 60 秒 | |
| 租约 | 结果不明的发送占名额至 120 秒到期，**不自动补发** | |

【代码：三条日额度与频率见 `platform/registration.js:271`、`:311`（`SEND_WINDOW_MS = 10 * 60 * 1000`，键为 `reg:<IP>`）；并发见 `:166-170`（上限固定 4）；`global_daily_limit` 见 `:35`/`:120`】

> **额度按北京时间自然日切分**，由 `quotaDay()` 硬编码 `+8h` 计算，**不依赖服务器时区**——这是功能性逻辑，不是显示问题。【代码：`platform/registration.js:96-99`、`db.js:380-381`】
>
> 邮件正文的「验证码有效至」时间同样用 `+8h` 计算。【代码：`platform/mail.js:68-71` 的 `shanghaiTime`，用于 `:83`】

## 7. 第 5 步：本机验证 + AC22 送达率验收

> ⚠️ **先读这条**：发码有**同 IP 5 次 / 10 分钟**的频率限制，`register` 与 `resend` 共用。【代码：`platform/registration.js:271`、`:311`】
>
> 本节的完整验收恰好需要 **5 次发码**（7.1 一次 + 7.3 四个收件域各一次）。**不要浪费任何一次在重试上**。如果中途出错用掉了次数，第 6 次会立刻返回 `429 rate_limited`——这是预期行为，不是发信故障，等 10 分钟即可。

### 7.1 触发一次真实发码

```bash
curl -s -X POST http://127.0.0.1:3000/api/account/register \
  -H 'Content-Type: application/json' \
  -d '{"registrationProtocol":"email-code-v1","email":"<你的测试收件邮箱>@163.com","password":"Test123456","nickname":"验收账号"}'
```

期望：`200`，且响应体**不含 `devCode` 字段**。

> **`registrationProtocol: "email-code-v1"` 是必填的**。缺它会返回 `409 client_upgrade_required`（「注册流程已更新，请刷新页面后重试」）。【代码：`platform/registration.js:5`、`:74`】
>
> 邮箱必须是**纯 ASCII 的真实地址**——中文占位符不替换会返 `400 invalid_input`。【代码：`platform/registration.js:57`】

### 7.2 确认没有掉进 dev 模式

两条硬性检查：

1. 上面的响应体里**不得出现 `devCode`**【代码：`platform/registration.js:245`，仅 `mode === 'dev'` 时附加】
2. `pm2 logs clawclash --lines 200 --nostream` 里**不得出现 `[开发验证码]`**【代码：`platform/mail.js:320`】

出现任一，都说明 `SMTP_HOST` 为空、进了 dev 模式——此时验证码会明文写进日志**并随 HTTP 响应体返回**。**绝不能在公网开放的服务器上处于这个状态。**

> `pm2 logs` 默认是流式 tail、不会自己结束，必须带 `--nostream`（或 `--lines N` 后按 Ctrl-C）。

### 7.3 AC22 真实收件验收（唯一「不做必然不可用」的项）

代码在 DATA 段收到最终 `250` 就算成功并计额度。【代码：`platform/mail.js:288-293`】**`accepted` ≠ 进了收件箱。** 所以必须人工开箱确认，四个主要收件域各测一次。

**最省事的做法**：重复运行 `node smtp-check.js`，每次只在第 3 个问题填不同的收件邮箱。它会真发一封并显示结果。（该工具直接调用发信模块，不经过平台注册服务，因此**不受平台 5 次/10 分钟的频控约束**——但仍要节制，别把自己的邮箱额度刷掉。）

| 收件域 | 是否收到 | 是否落垃圾箱 | 主题/正文/北京时间截止是否正常 | 状态 |
|---|---|---|---|---|
| 163 | ✅ | ✅ 收件箱 | 未核对 | ✅ 已通过 |
| QQ | ✅ | ✅ 收件箱 | 未核对 | ✅ 已通过 |
| hotmail / Outlook | ✅ | ✅ 收件箱 | 未核对 | ✅ 已通过 |
| Gmail | — | — | — | ⏭️ **主动放弃**（见下） |

> **⚠️ 以上全部是在开发者本地电脑的出口 IP 上测的，不是上海服务器的 IP。**
>
> 邮件的送达与否，**取决于发信那一方的 IP 在收件方眼里的信誉**。本地网络和上海轻量服务器的公网 IP 是两个完全不同的地址，网易对后者一无所知。因此**这张表目前只能证明「配置正确、代码没问题」，不能证明「上线后送得到」**。
>
> **必须在服务器上重跑一遍同样三项**（服务器部署完成、`ecosystem.config.js` 配好之后，在服务器上执行 `node smtp-check.js`）。这一步同时就是 3.4 的 IP 洗白。
>
> **而且不能只测一次就算完**：上海 IP 是新地址，网易对它的风控判定可能是渐进的（前几封通过、量上来后被限）。上线后头一周要盯着发信失败率。

> **关于放弃 Gmail 的决定**：这是可接受的选择，但请确认它是有意识的取舍——**如果目标用户里有人用 Gmail 注册，他收不到验证码就等于注册不了**，且不会有任何报错，只会看到「收不到验证码」。中文平台的主要用户群在国内，Gmail 本身访问受限，所以放弃测试是合理的；但如果你预期有海外用户，这一条要重新考虑。

### 7.4 查看发信日志

```bash
pm2 logs clawclash --lines 200 --nostream | grep -i smtp
```

> **成功发信不打印任何日志行。** 代码只在发信失败或存储失败时打日志。【代码：`platform/registration.js:250`，仅在 `outcome !== 'accepted'` 时执行】
>
> 所以「日志里没有 smtp 字样」是**好事**。成功以 7.1 的响应体不含 `devCode`、且邮箱确实收到为准。

失败时按错误码排查：

| 错误码 | 含义 | 处理 |
|---|---|---|
| `smtp_535` | 授权码错 / 未开 SMTP 服务 | 重新获取授权码 |
| `smtp_553` / `smtp_550` | 发件人与认证账号不符（也可能是认证未过） | 检查 `SMTP_FROM` 是否误设 |
| `smtp_554` | IP 被风控 | 见 3.4，先做 IP 洗白 |
| `smtp_421` | 并发或频率超限 | 见 13.2 |
| `smtp_transport_error` | 连不上、TLS 失败、超时 | 先跑 4.7 的连通性检查 |

> **同一个数字码可能有多种含义**，网易常在冒号后带字母码（如 `DT:SPM`、`HL:IHU`、`HL:ICC`、`MI:NHD`）。真正定位要看**冒号后的字母码**，数字码只是粗分类。【外部】

## 8. 第 6 步：安全加固

> 平台运行玩家提交的不可信 JS。代码层已有子进程隔离 + Node 权限模型，但**权限模型不拦网络出站**，逃逸脚本仍可对外连接。必须用 OS 层断掉 runner 的出站网络。【代码：SECURITY.md】
>
> **本节要在开放公网（第 9 节）之前完成。**

### 8.1 创建低权限用户并降权

```bash
useradd -r -s /usr/sbin/nologin clawbot
id -u clawbot    # 记下纯数字
id -g clawbot    # 记下纯数字
```

把两个**纯数字**填入 `ecosystem.config.js` 的 `RUNNER_UID` / `RUNNER_GID`，然后：

```bash
cd /www/wwwroot/clawclash
pm2 startOrRestart ecosystem.config.js
pm2 save
```

> **必须带文件名 `startOrRestart`。**`pm2 restart clawclash` 按名字重启**不会重读配置文件**，改的 env 不生效。

### 8.2 确认降权真的生效

```bash
ps -o user= -p $(pm2 pid clawclash)     # 期望 root（这是应用进程的属主）
pgrep -af runner.js                     # USER 列应为 clawbot
```

> 用 `pgrep -af` 而不是 `ps -eo user,pid,cmd | grep runner.js`：runner 的命令行很长（`--permission` + 两个 `--allow-fs-read` + 脚本绝对路径），`runner.js` 在行尾，`ps` 在非交互环境下常截断到 80 列而匹配不到。
>
> 用 `pm2 pid clawclash` 而不是 `ps -o user= -p $(pgrep -f pm2)`：前者取的是应用进程，后者会取到 PM2 God daemon。

两条都要做，因为：

- **`RUNNER_UID/GID` 填错不会被报错**，只会静默当作「未配置」→ 不降权。解析条件是「能转成整数且非空串」，占位符、用户名都会落空【代码：`platform/execpool.js:44-45`】
- **PM2 若以非 root 运行**，setuid 会失败，且执行池会挂死：spawn 失败被 `child.on('error')` 吞掉、补员不触发、挑选 worker 要求 `connected` 而失败进程恒为 false → 排队任务既不执行也不超时。【代码：`platform/execpool.js:112`、`:102`、`:120`】

指南 §3.1 写的「本指南 PM2 即 root 跑的，满足」是**未经确认的假设**，请实际验证。

### 8.3 禁掉 runner 的对外连接

```bash
iptables -A OUTPUT -m owner --uid-owner clawbot -o lo -j ACCEPT   # 兜底：万一 runner 走本机 TCP
iptables -A OUTPUT -m owner --uid-owner clawbot -j REJECT         # 丢弃其余对外连接
iptables -L OUTPUT -n --line-numbers                              # 确认两条规则在列
```

> 第一条是兜底而非必需——runner 与父进程的 IPC 走 fork 的 socketpair/管道，本就不经过 iptables。【代码：`platform/runner.js:19`、`:23`】
>
> 这两条只匹配 `clawbot`，root 主进程的 465 发信不受影响。

### 8.4 持久化（指南漏了这步）

`iptables -A` 只写运行时表，**服务器重启即失效**；而 5.2 配的 `pm2 startup` 会让应用开机自动拉起。结果是重启后**应用在跑、网络隔离悄悄消失**，且没有任何提示。

**按发行版选一种**（宝塔常见的是 CentOS）：

```bash
# CentOS / RHEL / 宝塔
mkdir -p /etc/sysconfig
iptables-save > /etc/sysconfig/iptables
systemctl enable --now iptables
```

```bash
# Debian / Ubuntu
mkdir -p /etc/iptables
apt-get install -y iptables-persistent
iptables-save > /etc/iptables/rules.v4
```

> 或改用宝塔「安全 → 系统防火墙 → 自定义规则」录入（宝塔会自行持久化）。
>
> **只写文件不会开机自动加载**，必须有对应的持久化服务。Debian 系的 `/etc/iptables/rules.v4` 路径在 CentOS 上不存在，直接重定向会报「No such file or directory」而 `iptables-save` 根本没执行——读者却以为已经落盘。
>
> **装完重启一次，验证规则仍在。**

> **两条常被忽略的细节**：① 只设 `RUNNER_GID` 不设 `RUNNER_UID`，setgid 会成功但进程仍以 root 跑，`--uid-owner` 规则同样空转——**两个都要填**；② 改过宝塔防火墙后要重跑 8.3 的两条命令（宝塔可能重建链）。

```bash
const src = new DatabaseSync('/www/wwwroot/clawclash/sixchess.db');
backup(src, dest).then(() => {
  const ok = new DatabaseSync(dest).prepare('PRAGMA integrity_check').get();
  console.log(dest, JSON.stringify(ok));
  if (ok.integrity_check !== 'ok') process.exit(1);
}).catch((e) => { console.error(e); process.exit(1); });
EOF
node /root/backup.js      # 应输出 {"integrity_check":"ok"}
```

> 该脚本已在 Node v26.4.0 上实测通过：`backup(src, dest)` 两参数签名正确，`PRAGMA integrity_check` 经 `.get()` 返回 `{"integrity_check":"ok"}`，生成的快照可被独立打开查询。
>
> **保留策略**：脚本按时间戳命名，不会自动清理。加一条 cron，只保留最近 14 份：
>
> ```bash
> ls -1t /root/backup/clawclash-*.db | tail -n +15 | xargs -r rm --
> ```
>
> **SECURITY.md 要求发布前在生产数据副本上演练一次恢复**——别只备份不演练。

### 12.4 回退：紧急暂停发码

代码里**没有**暂停注册的开关或运维端点。【代码：全仓 `process.env.*` 直接读取的有 `SESSION_SECRET / NODE_ENV / DB_PATH / PORT / PUBLIC_ORIGIN / RUNNER_POOL_SIZE / RUNNER_UID / RUNNER_GID / CHILD_PERMISSION`，另有经 `loadConfig(env = process.env)` 读取的 `SMTP_HOST/SECURE/PORT/USER/PASS/FROM/DAILY_MAX` 七个【代码：`platform/mail.js:25-56`】；无 `REGISTRATION_ENABLED` 之类】

**唯一不改代码的手段**：把 `SMTP_HOST` 设为**空串**（`SMTP_HOST: ''`），然后：

```bash
pm2 startOrRestart ecosystem.config.js
```

此时 `register` / `resend` 返回 `503 mail_unavailable`，**登录、核验、游戏全部不受影响**。【代码：`platform/mail.js:44` 空串 → `unavailable('invalid_host')`；`platform/registration.js:150-153`】

> ⚠️ **危险：不要「注释掉」或「删掉」`SMTP_HOST` 这一行。**
>
> 键不存在（`undefined`）时的行为与空串完全不同：在**未设 `NODE_ENV`** 的环境里会退化成 `mode: 'dev'`——`register` 返回 **200**，验证码进响应体（`devCode`）与日志。【代码：`platform/mail.js:58-61`、`platform/registration.js:245`、`platform/mail.js:320`】
>
> **设为空串 → 503（安全）；删掉整行 → 泄露验证码（危险）。** 这二者只差一个引号。
>
> **验证回退生效**：启动日志应出现 `[注册邮件不可用] invalid_host`【代码：`server.js:31-32`】，且真发一次码应返回 `503`。看到 `200` 就说明写错了，立刻改回并重启。

> 恢复时把真实主机名填回 `SMTP_HOST` 再重启。**禁止重开旧直建号接口，也不要删除新账号或清空成功发信账本。**

## 13. 网易特有风险与缓解

### 13.1 送达率

用**免费个人网易邮箱**给任意用户填的邮箱发验证码，是网易反垃圾风控的典型命中特征。可能的后果：账号被限流或暂停发信（**时长网易不公开**）。【外部，判定规则与时长均无公开依据】

用户侧的表现取决于网易怎么拒：

- **网易回 5xx** → 平台记为失败，**不占额度、冷却也不生效**，重试即可
- **网易回 250 但静默丢弃** → 平台记为成功、**扣额度**，用户却收不到——这才是真正难排查的那种

【代码：`db.js:380-381` 日额度只统计 `state='sent'`；失败经 `finishRegistrationMail` 置 `failed` 并释放预留；`checkCooldown` 只在 accepted 后生效】

**缓解**：
- 上线前完成 3.4 的 IP 洗白
- 7.3 的 AC22 四域送达验收必须真做
- 把「出现大量发信失败时先按 12.4 暂停发码，而不是硬顶」写进运维日志

**长期**：个人免费邮箱只适合灰度验证。要正经运营，建议换网易企业邮箱（`smtp.qiye.163.com`）或专门的发信服务。

### 13.2 并发风控

平台允许同时最多 4 条到 `smtp.163.com` 的连接，满时返回 `503 send_busy` 而非排队。【代码：`platform/registration.js:166-170`，上限固定 4；`:186` 返回 `send_busy`】

网易对并发连接数与短时频率有风控，超限返 `421` 临时禁止连接，表现为发信失败且**无自动退避**。【外部】

**缓解**：上线初期观察一周；若频繁出现 `421`，需要把这个上限做成可配项并降到 1–2。

### 15.1 一个建议尽快修的安全洞

`sendJson` 给**所有**响应固定加了 `Access-Control-Allow-Origin: *`，OPTIONS 预检放行，而三个注册路由**没有任何 Origin/CSRF 校验**。【代码：`server.js:57`、`server.js:256-270`、`server.js:430`】

后果不只是隐私问题：第三方页面可以让访客的浏览器向 `/api/account/register` 灌任意邮箱，**打光每 IP 与全局的每日额度**，把正常注册整体打死，同时把「脚本化群发」的特征喂给网易风控（与 13.1 是同一风险的放大器）。

**上线初期**靠「3000 端口只在验证的那几分钟开放」可缓解，但作为公网服务这是应该修的。最小修法是给 register/resend 加同源 Origin 校验。
