# 更新部署上线指南（v1.0）

> **用途**：网站代码有改动后，把新版本安全地更新到线上 https://clawclash.cn 的完整流程。
> **这份指南写给两个人看**：网站所有者（你，只做第 3、4 步和看结果）和协助的 Claude 会话（其余步骤）。
> **依据**：2026-10-10 首次使用自动部署脚本的完整实操（版本 `b78b9f1`，停机约 5 秒）。最近一次的详细记录见 [同步说明_2026-10-10](Agent指南与安全修复同步说明_2026-10-10.md) 文末「部署记录」。
> **相关文档**：[运维速查_非技术版](运维速查_非技术版_v1.0.md)（日常运维速查卡）、[上线操作手册](上线操作手册_网易邮箱_v1.0.md)（服务器背景与排障）。

## 0. 总览：一次更新 = 6 步

| 步骤 | 谁做 | 做什么 | 耗时 |
|---|---|---|---|
| 1. 改代码 + 测试 | Claude | 改动、全量测试全绿、提交并推送 | — |
| 2. 打代码包 | Claude | 生成 `clawclash-deploy-<版本号>.zip` 并校验、记下「部署前基线」 | 2 分钟 |
| 3. 上传 | **你**（浏览器） | 宝塔 → 文件 → 上传到 `/www/wwwroot/clawclash` | 1 分钟 |
| 4. 一键部署 | **你**（宝塔终端，粘一条命令） | 脚本自动：备份 → 停服几秒 → 覆盖 → 重启 → 自检（失败自动回退） | 1–2 分钟 |
| 5. 验证 | 脚本自检 + Claude 外网核验 + 你可选看两眼浏览器 | 对照第 5 节清单 | 2 分钟 |
| 6. 记录收尾 | Claude | 写部署记录、更新 QA/文档/记忆、提交推送 | — |

**为什么这么谨慎**：本项目没有独立测试环境，线上就是正式环境。所以每次都走固定保险流程——先备份、留好后路（回退包）、部署后自检、失败自动还原。**永远不要**在服务器上手改代码或用别的野路子更新。

## 1. 部署前检查（Claude 执行，全部满足才继续）

- [ ] **全量测试通过**（两条命令都要）：
  - `node --test --test-concurrency=1`（相当于 `npm test` 的直接写法；本机曾遇 npm 包装入口异常，直接跑 node 命令最稳）
  - `npm run test:rules`
- [ ] **改动已提交并推送** `origin/main`（`git status` 干净；服务器虽然连不上 GitHub，仓库仍要留痕）
- [ ] **版本差异体检**：`git diff --name-status <线上版本>..HEAD`
  - 有**删除**文件？→ 服务器上的旧文件不会被自动删掉（Node 只加载被引用的文件，通常无害）；若删除的是 `public/` 下静态文件，部署后需在宝塔文件管理里手动删，否则老 URL 还能访问到
  - 动了 **`db.js` / 迁移逻辑**？→ 走附录 C 的特殊流程
  - 动了 **`deploy.js` 本身**？→ 必须先本地演练（附录 B 有命令）
- [ ] **确定「新版本标记」**：从本次新增/修改的指南文字里挑一句**新指南必有、旧指南必无**的短语（例如 2026-10-10 版用的是「各有约 10 秒」）。
  - 部署时默认用 deploy.js 里写死的标记；若本次指南措辞变了，部署命令前加环境变量覆盖即可（见第 4 节说明），Claude 负责选句
- [ ] **记录部署前基线**（用于部署后对照）：从外网跑一次
  `curl -s https://clawclash.cn/games/darkchess/agent-guide | grep -c "新标记句子"` → 期望 0
- [ ] **低峰期执行**（夜里），并确认 Claude 在线可随时处理

## 2. 打代码包（Claude 执行）

```bash
git archive --format=zip -o clawclash-deploy-<7位提交号>.zip HEAD
```

命名规矩：`clawclash-deploy-<7位提交号>.zip`，例：`clawclash-deploy-b78b9f1.zip`。**包名用英文**，全程不要空格。

打包后必须校验（全过才算合格）：

```bash
unzip -t clawclash-deploy-<版本>.zip                  # 期望最后一行含 "No errors detected"
unzip -Z1 clawclash-deploy-<版本>.zip | grep -x "server.js" -e "deploy.js"   # 关键文件必须在
```

- **必须包含**：`server.js`、`deploy.js`、本次改动的所有关键文件
- **绝对不能包含**：`sixchess.db*`（数据库）、`ecosystem.config.js`（密钥）、`public/avatars/*`（用户头像）——`git archive` 会自动排除；若出现说明打包方式错了
- 打完把 zip 通过聊天文件卡片发给所有者

> 附注：代码包是随时可重建的——哪天本地文件找不到了（比如被挪去了「下载」目录，或被清理），用上面这条 `git archive` 命令就能原样重打一份；服务器 `/root/backup/` 里也留有历次代码包的归档。

## 4. 一键部署（所有者执行）

⚠️ 命令要粘贴在【**宝塔面板左侧的「终端」**】里回车（不是在你电脑上，也不是在聊天里点运行）。**把下面两处包名都换成你实际的文件名**：

```bash
cd /www/wwwroot/clawclash && unzip -o clawclash-deploy-b78b9f1.zip deploy.js && node deploy.js clawclash-deploy-b78b9f1.zip
```

回车后等它自己跑完（1–2 分钟；**期间网站中断约 5 秒，属正常**，别关窗口）。脚本会自动依次做：

1. 预检：代码包完整性、关键文件、确认包里不含数据库/密钥/头像（此阶段不碰服务器）
2. 备份数据库（确认 `integrity ok`）、备份密钥配置、生成**回退包**并自检
3. 停服 → 覆盖代码 → 重启
4. 体检：进程在线 + 接口返回 200 + **新版本标记命中**（证明新代码真的在跑）

### 两种结局，认准开头几个字

- **`结果: 【成功】网站已运行新版本。`** → 更新完成，进入第 5 节验证
- **`【回退成功】`** → 新版本有问题、已**自动还原**回更新前，网站是好的 → 把输出发给 Claude 分析即可，然后重复流程
- **`【中止】`（未停服）** → 前置检查没过，网站完全没被碰过 → 把输出发给 Claude

> **关于「新版本标记」**：脚本用一句新指南里的话来证明"新代码真的在跑"。若本次更新改了指南措辞，Claude 会在命令前加一句环境变量来替换标记，例如：
> `CC_GUIDE_MARKER='新句子' node deploy.js 包名.zip`（这是 Claude 的活，你不用记）

### 跑完后

把终端里**从脚本标题开始的全部输出**复制发回给 Claude。

## 6. 出问题了怎么办（先别慌）

| 现象 | 含义 | 你做什么 |
|---|---|---|
| 输出含 `【回退成功】` | 新版本有问题，网站**已自动还原** | 把输出发 Claude；网站照常可用 |
| 输出含 `【中止】` | 前置检查没过，**服务器没动过** | 同上 |
| 命令跑完网站打不开 | 极少数情况（回退也失败） | 把输出发 Claude；随后按 Claude 给的一条条诊断命令粘贴 |
| 部署成功但页面显示怪 | 多半是浏览器缓存 | `Ctrl+F5` 强制刷新；还不对再找 Claude |

**手动回退命令**（脚本每次结束时都会打印现成的一行，形如；只在需要立即恢复时用）：

```bash
tar -xzf /root/backup/code-rollback-<时间戳>.tar.gz -C /www/wwwroot/clawclash && cd /www/wwwroot/clawclash && pm2 startOrRestart ecosystem.config.js && pm2 save
```

**数据库回退**：极少用、**有数据丢失风险，动手前必须先问 Claude**（流程见《上线操作手册》12.2）。

**三条永远不要碰的红线**（与《运维速查》§4 一致）：

- 不要删 `/root/backup/` 里的任何东西——那是所有「后悔药」
- 不要改/删 `ecosystem.config.js`——密钥在里面，仓库里没有
- 不要动 iptables / clawclash-egress 服务——那是关住用户机器人脚本的安全笼子

## 附录 C：特殊情况——涉及数据库/迁移的更新

- **动了 `db.js` 或启动迁移逻辑**：先跑全量测试（`test/migration.e2e.test.js` 在内）；部署前用最近一次数据库备份在本地/副本上演练一遍启动迁移；部署记录里必须写明"迁移已变更"，并评估回退时的兼容性（加表加列一般向后兼容；改列/删列需要专门评估，回退可能需连数据库一起还原）。
- **删除了仓库文件**：见第 1 节的处理说明（服务器旧文件残留；`public/` 下需手动删）。
- **动了 `deploy.js` 本身**：必须先在本地假目录完整演练（附录 B 第二条），确认预检/备份/回退包/解压/（可选）回退逻辑都走通，再打包发布。
