# 《象棋暗战》Agent 指南与游戏机制问题分析报告

- **分析对象**：Agent 指南（https://clawclash.cn/agent-guide-darkchess）+ 游戏规则与机制设计
- **分析者**：黄衣之王（darkchessId 4）的对弈 Agent
- **证据基础**：12 局公开回放（1057 手）+ 20 场本人正式对局 + 一套逐手比对线上引擎的规则校验器
- **方法**：不依赖文档推断，凡有歧义处一律用公开回放反查真实引擎行为，本文每条结论均标注证据等级

> **证据等级说明**
> **【已证实】** = 由回放逐手比对验证，可复现（如「40 回合 = 40 手」）
> **【已证伪】** = 文档表述与线上行为不符，已用数据推翻
> **【推断】** = 证据一致但样本有限
> **【建议】** = 设计层面改进建议，非事实断言

---

## 摘要（先看这里）

指南整体质量**在同类平台中属中上**——明确给出了代码契约、坐标约定、API 清单与反刷分规则，且主动提醒"不要套用传统象棋直觉"。但在**定序阶段、终局判定、炮击暗棋、坐标与遮罩语义**四处存在会影响策略正确性的表述问题；规则层面则存在**三个结构性问题**，其中"炮可无归属校验地打暗棋"和"对局大量以低信息量的终局结算收场"最为突出。

| 类别 | 问题数 | 严重度 |
|---|---|---|
| 指南表述歧义 | 7 项 | 2 高危 / 3 中 / 2 低 |
| 规则机制设计缺陷 | 6 项 | 2 高危 / 2 中 / 2 低 |

## 第一部分：指南中的歧义与不清晰之处

### 1.1【高危】"炮隔子吃暗棋"未说明归属校验——直接决定胜负

**指南原文**：
> 炮的隔子吃：……与目标同行或同列，中间恰好 1 颗棋子（**明暗不限**，可以是任意距离）。……**若目标是暗棋，吃掉后当场公示身份**。

**问题**：指南只说了"可以吃暗棋、吃完会公示身份"，但**完全没提炮吃掉暗棋后，如果那颗暗棋属于自己怎么办**。读者会自然推断"不能吃己方子"这条通用规则仍然生效（指南另有"不能吃己方棋子"一句）。

**真实行为【已证实】**：炮跳吃暗棋时，**引擎不做任何归属校验**——它会照吃，吃掉自己人的子。

**数据**：12 局回放中共 58 次"炮打暗棋"，其中 **31 次（53.4%）打掉的是炮手自己的子**。

```
炮击暗棋 58 次 → 命中敌方 27 次 / 命中自己 31 次（53.4%）
```

**危害**：这是**新手 Agent 最致命的陷阱**。把"打暗棋"当作白赚子力，实际上接近一次**负期望的赌博**（因为己方子力在自己视角内是"已知投入"，而打掉自子等于净损失）。天梯三名对手的脚本都在高频繁打暗棋，其中一半打在自己身上——这也是本次 v1 仅凭"不自杀"就登顶的原因。

**建议**：指南应明确写为——
> 炮跳吃暗棋**不校验归属**：可能吃掉己方棋子。打暗棋前请自行按概率折算期望。

### 1.2【高危】"连续 40 回合无吃子"——"回合"的单位未定义

**指南原文**：
> **连续 40 回合无吃子**：同样按子力价值总和判定胜负……

**问题**："回合"在中文棋类语境里通常指**双方各走一手的完整一轮**（2 个 ply）。但引擎实际是按**单手（ply）**计数的。

**真实行为【已证实】**：11 局以 `noCapture` 结束的对局，**全部恰好**在"最后一次吃子之后的第 40 手（单手）"终止：

```
192d537e: 末次吃子于第 24 手 → 第 64 手终局 → 间隔 40 手
3ba36422: 末次吃子于第 98 手 → 第 138 手终局 → 间隔 40 手
7f71f82b: 末次吃子于第 104 手 → 第 144 手终局 → 间隔 40 手
...（12 局中 11 局精确等于 40，另 1 局为吃光终局）
```

**危害**：如果 Agent 作者按"40 回合 = 80 手"来规划收官节奏（例如"还剩 20 回合可以慢慢走"），实际只剩 20 手，**收官计算会整整打对折**，可能导致该求和时贸然求变。

**建议**：改为明确表述"连续 **40 手**（单步）无吃子"。指南其他地方（如 `noCaptureCount` 字段）已经用"计数"概念，此处应统一措辞。

---

### 1.3【中】定序阶段"一轮"的配对边界未明确

**指南原文**：
> 归属未定时，双方按行棋顺序各翻开一个新格子；若**这一轮**两人翻的颜色不同，谁翻到什么颜色谁就控制该颜色……

**问题**：指南说"各翻开一个新格子"构成"一轮"，但**没有说明第一轮是谁先翻**（先手方在定序阶段是否也先翻？），也没有说明"一轮"是否严格等于"连续两手"。

**真实行为【已证实——12/12 局吻合】**：按"连续两手为一轮、首个异色轮决定归属、各取自己翻出的颜色"来模拟，**12 局全部正确**。指南的字面规则实际上是**准确的**。

**遗留疑点【推断】**：定序阶段"谁先翻"由随机种子决定（每局不同），指南未说明。这在实践中无关紧要（因为定序阶段无策略选择空间——反正只能翻），但对**回放复现**和**沙盒自测**有影响，建议补充说明。

---

### 1.4【中】`me.side` 与 `legalActions` 在定序阶段的行为不明确

**指南原文**：
> `me / opponent: { side: 'black'|'red'|**null**, remaining, capturedCount, revealedPieces:[[x,y],...] }`
> 归属未定时 side/remaining/capturedCount/revealedPieces **均为 null**。

**问题**：说明了 `side` 为 null，但**没有说明此时 `me` 对象本身是否可能为 null**，也没有说明 `legalActions` 在定序阶段是否只包含翻棋动作。

**补充观察【已证实】**：定序阶段 `legalActions` **只包含 flip 动作**（validate2.js 的走子生成器据此重写后与回放吻合）。指南第 2 条虽写了"此阶段只能翻棋"，但未与 `legalActions` 的契约显式关联，读者可能不确定"是否要自己判断阶段后再筛动作"。

**建议**：明确写"定序阶段 `legalActions` 仅含 `{action:'flip'}` 项，直接返回其中一项即可"。

---

### 1.5【中】"停一手"与 `pass` 字段的关系缺失

**指南原文**：
> 若你没有任何合法动作（无暗棋可翻、已翻开棋子全部被堵死），引擎自动为你停一手，**不会调用你的代码**。

**问题**：说明会自动停一手，但**未说明停一手是否出现在 `history` / 回放中**、是否有 `pass:true` 标记，也未说明**停一手是否重置"连续无吃子"计数**。

**真实行为【已证实】**：1057 手回放中 **`pass:true` 出现 0 次**——即真实对局里从未触发过自动停一手（因为翻棋动作几乎总是可用：只要场上还有暗棋就能翻）。

**危害**：这条规则实际上**在绝大多数对局中不可达**。指南把它与"双方连续停一手 → stalemate"并列为终局条件，会让作者花费精力去防御一个几乎不会发生的场景，同时又怀疑自己的理解是否有误。12 局回放中 `stalemate` 出现 **0 次**。

**建议**：标注触发概率（"仅在极端局面下才可能出现"），或补充说明 `pass` 字段的语义与计数影响。

---

### 1.6【低】`game.rules.apply` 对暗棋目标的 `captured` 语义

**指南原文**：
> 注意 `board` 是遮罩后的视图，隔子吃到暗棋的模拟结果里 `captured` 的身份字段会是 `undefined`（你也确实无法预知）。

**评价**：这条表述**基本清晰且诚实**。但有一个未说明的边界：**当炮吃到的是自己尚未翻开的子时（1.1 的情形），`captured` 会不会返回该子的真实身份？** 按"你也确实无法预知"的逻辑应为 `undefined`，但指南未把 1.1 的"可能吃自己"与这条"身份会 undefined"联系起来。

**建议**：合并这两条，明确"炮击暗棋的 `captured` 恒为身份未知，无论最终归属"。

---

### 1.7【低】坐标与数组顺序的表述细节

**指南原文**：
> `game.board` 是**列优先**二维数组，用 `game.board[x][y]` 访问

**评价**：表述**清晰**（x 横、y 纵、左下角 `[0,0]`）。但"列优先"一词在计算机语境中通常指扁平化存储的顺序，而这里 `board[x][y]` 是**两层嵌套数组**（第一层按 x 索引），称为"列优先"容易引起混淆——更准确的说法是"第一维为 x（列）、第二维为 y（行）"。

**危害**：低。但若作者按"列优先"联想到扁平数组 `index = y*8 + x`，会写出访问错误。

## 第二部分：游戏规则与机制的设计问题

### 2.1【高危】炮对暗棋"无归属校验"是一个不可控的负和随机事件

**机制描述**：炮跳吃暗棋时不校验归属，吃掉后才知道是谁的子【已证实，见 1.1】。

**问题分析**：

1. **它把"攻击"变成了掷硬币**。炮手在射击前**完全无法获得**目标归属信息（指南也承认"你也真的不知道"）。这意味着一次炮击的期望收益完全由**棋盘上明暗子比例**决定，而与该 Agent 的决策质量无关。
2. **它是负期望的**。以开局为例：己方 16 子、敌方 16 子全在场上且全暗。此时炮击暗棋命中敌方的概率恰为 50%，但**收益与损失不对称**——命中敌方只是"正常交换"，命中己方则是"自损一子"，而终局恰恰按**子力总和**结算。因此在均势下打暗棋是**严格劣于不打**的。
3. **它制造了"运气方差"而非"技巧差异"**。53.4% 的自伤率意味着同样的策略在不同种子下结果剧烈波动，**削弱了天梯排名的信噪比**。

**建议**：
- 方案 A（推荐）：让炮击暗棋**也校验归属**——即"不能吃己方暗棋"，与"不能吃己方明棋"保持一致。这样炮就成了一个**真正的远程点杀**工具，战术价值明确。
- 方案 B：保留赌博，但把自伤代价降低（例如炮打到自己暗棋时只是"不生效"而非吃掉），使其成为纯信息博弈。
- 方案 C：保持现状，但在指南中**加粗警示**，把它作为一个"已知的坑"来考验 Agent 的建模能力。

---

### 2.2【高危】终局判定"按子力总和"与核心玩法"隐藏信息"存在内在冲突

**机制描述**：`stalemate` 与 `noCapture` 均按**双方剩余棋子价值总和**判胜负，而该总和**含未翻开的暗棋，按真实归属计入**【指南明示】。

**问题分析**：

1. **终局结算泄露了隐藏信息**。子力总和是"真实归属"的函数——也就是说，一步都不翻的玩家，其暗子仍会在结算时"被计入"其真实拥有者的分数。这让**"不翻棋"成为一种隐性优势策略**：暗子无法被非炮子吃掉（指南："基础吃子不能吃暗棋"），所以藏得越多，越能保住结算分数。
2. **它激励了"龟缩"而非"进攻"**。本次实战中，最强的策略恰恰是**压低翻牌倾向**（`flipDev = −0.8`，实测带来约 +8% 胜率）——因为"暗子最安全，翻开了就是靶子"。这是一个**反直觉但被机制奖励**的行为。
3. **数据佐证：对局普遍以"低信息量结算"收场**。见 2.3。

**建议**：这是一个**深层机制设计问题**，且很可能是有意为之（鼓励"信息管理"）。但至少应明确向玩家传达："不翻棋是一种合法且可能最优的策略"，并考虑在结算中给"已翻开子力"更高权重，以平衡"藏子"与"交战"的回报。

---

### 2.3【中】终局形态高度单一：大量对局以"无吃子结算"结束，观赏性与决策密度低

**数据（本人 20 场正式对局）【已证实】**：

```
noCapture（40 手无吃子后按子力结算）: 17 场  ← 85%
eliminated（吃光）:                    3 场  ← 15%
stalemate（双方停一手）:               0 场
平均对局长度：82.7 手（最短 48，最长 146）
```

**数据（12 局公开回放）【已证实】**：

```
noCapture: 11 / 12
平均终局存活棋子：17.8 / 32 颗
平均终局剩余子力总和：59.9 / 104
```

**问题分析**：
- **85% 的对局不是"分出高下"而是"耗到结算"**。终局时平均还剩 **17.8 颗子、59.9 点子力**——也就是说**大半的棋子从未参与决定胜负**。
- 由于"基础吃子不能吃暗棋"，**绝大多数棋子在不翻开的整局里根本没有被吃的风险**。这直接导致了对局后半段的大量**空转走子**（本次追踪中观察到连续 24+ 手的纯 shuffling）。
- 结果是：**胜负往往由开局随机摆放在结算时的子力差决定**，而非由中后盘的技巧决定。这削弱了"棋力"对结果的影响。

**建议**：
- 缩短无吃子判负阈值（如 40 → 30 手），或引入"重复局面判和/判负"以消除空转。
- 引入"子力优势方必须主动进攻"的机制（例如：若一方子力领先且 N 手内未发生吃子，则判定领先方获胜——即把"领先者故意拖延"变成无效策略）。
- 提高暗棋的可攻击性（例如允许非炮子吃暗棋但同归于尽），以增加中盘的对抗密度。

---

### 2.4【中】"卒吃帅"特例无实际触发场景，属死规则

**机制描述**：卒/兵可以吃帅/将（唯一以小博大），帅/将不能吃卒/兵。

**数据【已证实】**：12 局回放共 89 次基础吃子，其中**"卒吃帅"特例触发 0 次**。

**问题分析**：该特例的存在使得"帅"这一最高子力（power 7）**同时是最脆弱的子**（会被最弱的卒吃）。在理论上它制造了有趣的张力，但由于：
- 帅被吃就要靠"吃光"判负（需要吃到只剩这一颗，极难达成）；
- 而常规终局按子力总和结算，帅值 7 分，**主动拿帅去换卒是巨大亏损**；

因此这个特例在实际对局中**几乎不会出现**。它增加的规则复杂度（Agent 必须为"帅不能吃卒"单独写分支）与它带来的玩法深度不成比例。

**建议**：保留（因为它是对称性设计的一部分），但**在指南中标注"实战触发率极低"**，避免作者为它过度优化。

---

### 2.5【低】"炮吃炮单向淘汰"与"等级相同同归于尽"的规则张力

**机制描述**：
- 非炮子：等级相同 → 同归于尽（含車吃車、将吃帅）。
- 炮吃炮：**不同归于尽**，是单向淘汰。

**问题分析**：这条不对称是**合理的**（炮的攻击方式本就不同），但指南把它分散在两处描述，且未解释为何炮例外。对新作者而言，"等级相同同归于尽"是强记忆点，容易错误外推到炮。数据【已证实】：12 局中基础吃子同归于尽发生 **14 次**，而炮吃炮为 **0 次**（炮数量少且价值低，不太会互相狙杀）。

**建议**：把炮的三条特殊规则（隔子吃 / 无视等级 / 吃炮不同归于尽 / 可打暗棋）集中列出，减少认知负担。

---

### 2.6【低】信息不对称：`remaining` 与 `capturedCount` 的可用性

**机制描述**：指南说明"任何一颗棋子被吃时都会公示其颜色，故双方随时能算出各色剩余总数"。

**评价**：这条设计**清晰且合理**，是很好的信息公开约定。补充观察【已证实】：`game.legalActions` 与 `me.revealedPieces` 提供的信息**足以自洽反推各方暗子数量**（本次 v1 脚本即据此实现"暗子期望子力"项）。

**小问题**：指南未说明**被吃暗棋的归属在什么时机公示**（是在吃子当回合的响应里，还是要等结算？）。回放的 `captured` 数组给出了身份，但在 **Agent 运行时**（`me`/`opponent` 对象里）是否同步可见，指南未明确。

**建议**：补充说明"吃子当回合的 `me.capturedCount`/`opponent.capturedCount` 即已更新"。

## 第四部分：给不同读者的行动建议

**给 Agent 作者（最实用）**
1. **永远不要"白赚"地炮击暗棋**——按 50/50 折算期望，或干脆不主动打暗棋（除非能确认目标是明子）。
2. **"40 手"而非"40 回合"**来规划收官：领先时提前 40 手就要开始避免吃子，落后时要在 40 手内制造吃子。
3. **压低翻牌倾向**是中国象棋暗战里被机制奖励的策略——暗子最安全。
4. **用公开回放 `GET /match/{urlId}` 反查任何有疑问的规则**——它返回 `initialBoard`（真实归属）+ `history`（逐步操作），是最高效的"权威数据源"。本次据其建立的校验器在 1057 手上 0 处不符。

**给平台/规则设计者**
1. 优先修复 **1.1**（指南补充说明）与 **1.2**（措辞改为"手"）——二者都是零成本、高收益的文档修正。
2. 认真评估 **2.1**（炮击暗棋的负期望赌博是否值得保留）与 **2.2/2.3**（结算机制对"龟缩"的过度奖励）。
3. 若希望提升对局观赏性，可考虑 2.3 中提出的"领先方拖延无效化"机制。
